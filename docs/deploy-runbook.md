# Runbook: первый запуск на чистом VPS (Ubuntu LTS, amd64)

Документ для человека, который сидит за свежим сервером и хочет получить
работающего бота, ничего не додумывая. Каждый шаг — команда и то, что должно
появиться на экране. Секретов в этом файле нет и быть не должно.

## Чему здесь можно верить

Проект собирался и проверялся **только на arm64-Маке через эмуляцию**. Ни один
настоящий amd64-хост образ ещё не запускал. Поэтому каждый раздел помечен:

- **[проверено локально]** — команда выполнена на Маке в эмулированном
  `linux/amd64`-образе, вывод в разделе «Что и чем проверено» в конце файла;
- **[только на сервере]** — проверить негде, кроме сервера; такие шаги собраны
  ещё раз в чеклисте первого запуска (§9), там же — ожидаемый вывод.

Строки «должно быть на экране» без пометки — из локального прогона; на сервере
они могут отличаться версиями и таймингами, но не смыслом.

## 0. Что нужно иметь до начала

| Что | Зачем | Откуда |
|---|---|---|
| VPS amd64, Ubuntu LTS, root или sudo | образ существует только под amd64 (`eval7` не публикует ни колёс, ни исходников под arm64) | провайдер |
| Доступ к @BotFather | токен бота придётся выпустить заново: старый утёк в логи и в `traces` до `f775d06` | Телеграм |
| Доступ к консоли провайдера | ключ придётся выпустить заново; тот, что на Маке, остаётся на Маке | консоль провайдера |
| Доступ по ssh с Мака | промпты моделей едут на сервер отдельно от гита | ключ на сервере |
| Каталоги промптов на рабочей машине | их нет в репозитории | `src/harness/*/prompts/` |

Оба секрета выпускаются заново **на шаге §5**, а не сейчас. Здесь нужен только
доступ к местам, где их выпускают.

**Почему не сейчас.** Отзыв токена в BotFather необратим и мгновенен: с этой
секунды старый токен мёртв, и бот не отвечает игрокам, пока новый не доедет до
§8. Между §0 и §8 лежат установка Docker, клон, доставка промптов и сборка — то
есть всё, что может занять часы и упасть на середине. Отозвав токен первым
действием, вернуться некуда: старый не восстанавливается. Поэтому порядок такой —
сначала довести сервер до состояния «осталось заполнить `.env` и стартовать», и
только тогда отзывать.

Ключ провайдера отзывается по тому же правилу и в том же месте, хотя цена ошибки
у него ниже: новый ключ можно выпустить, не убивая старый, — тогда простоя не
будет вовсе.

## 1. Сервер: пакеты и Docker **[только на сервере]**

```bash
sudo apt-get update
sudo apt-get install -y ca-certificates curl git rsync
sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/ubuntu/gpg | sudo tee /etc/apt/keyrings/docker.asc >/dev/null
sudo chmod a+r /etc/apt/keyrings/docker.asc
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] \
https://download.docker.com/linux/ubuntu $(. /etc/os-release && echo "$VERSION_CODENAME") stable" \
  | sudo tee /etc/apt/sources.list.d/docker.list >/dev/null
sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
```

Проверка:

```bash
uname -m                  # x86_64 — иначе дальше идти нельзя, образ arm не соберётся
docker compose version    # Docker Compose version v2.x или новее
docker run --rm hello-world
```

`docker compose` (без дефиса) — обязательно плагин v2: файл `docker-compose.yml`
использует `env_file: [{path:, required:}]` и `x-`-якорь, старый `docker-compose`
их не понимает.

**Ресурсы.** Образ занимает ≈720 МБ в выводе `docker images` [проверено
локально]. Сборка тянет колёса numpy/pokerkit/eval7 и компилирует байткод —
на машине с 1 ГБ памяти это первый кандидат на OOM; сколько именно нужно, не
измерено ни на одном сервере. Если памяти 1–2 ГБ, заведите swap до сборки.

Память покоя, `docker stats` сразу после старта [проверено локально, под
эмуляцией amd64 на Маке]: postgres 24–33 МБ, бот 256 МБ, воркер 325 МБ — вместе
≈615 МБ, и это до первой работы. Плюс сам Docker, systemd и sshd. Числа сняты
под эмуляцией и на сервере могут быть ниже, но 1 ГБ памяти они не оставляют
запаса ни на разбор, ни на сборку. **Минимум 2 ГБ, спокойно — 4 ГБ.**

Стоимость разбора, один процесс, холодный кэш, `analyze_hand` по всем точкам
[проверено локально, нативно на ARM]: 318 рук / 402 точки = 114 с процессорного
времени, то есть ≈0.36 с на руку и ≈70 с на турнир из 172 рук; пик RSS самого
разбора 148 МБ. На ядре сервера ждать в полтора-два раза дольше.

Про число ядер: тяжёлый счёт уходит в процессный пул размером `os.cpu_count()`
хоста — см. комментарий к сервису `worker` в `docker-compose.yml`. На 1 vCPU
пул вырождается в один процесс: турниры считаются по очереди, и на время
разбора ядро занято полностью.

## 2. Пользователь и каталог **[только на сервере]**

```bash
sudo adduser --disabled-password --gecos "" harness
sudo usermod -aG docker harness
sudo mkdir -p /srv/poker-harness
```

Дальше всё — от пользователя `harness` (`sudo -iu harness`). Членство в группе
`docker` равносильно root на этой машине; это осознанный размен, чтобы деплой не
шёл через sudo на каждую команду.

## 4. Приватные файлы: промпты моделей **[только на сервере]**

**Клон репозитория промптов не содержит.** Оба каталога закрыты политикой
публикации (`docs/publishing-policy.md`) и хуком: в гите их нет ни в каком виде.
Без них процессы стартуют и работают, HH-скан считается полностью, а первый же
вызов модели падает `PromptUnavailable` с именем файла.

С рабочей машины (не с сервера):

```bash
rsync -av src/harness/parsers/prompts/      harness@<сервер>:/srv/poker-harness/src/harness/parsers/prompts/
rsync -av src/harness/explanation/prompts/  harness@<сервер>:/srv/poker-harness/src/harness/explanation/prompts/
```

На сервере:

```bash
find src/harness -path '*/prompts/*.md' | sort
```

Должно быть ровно три строки:

```
src/harness/explanation/prompts/tournament.md
src/harness/explanation/prompts/verdict.md
src/harness/parsers/prompts/vision.md
```

И ещё одна проверка — что они не собираются уехать обратно в гит:

```bash
git status --porcelain | grep prompts    # пусто: каталоги в .gitignore
```

**Порядок обязателен: промпты кладутся ДО `docker compose build`.** Образ
забирает их тем же `COPY src ./src`, что и код; собранный без них образ
доставкой файлов на диск не чинится — нужна пересборка. По той же причине
любое изменение промпта = пересборка образа, а не только копирование.

Два конца, которые держат промпты внутри образа (оба — код, а не память):
`.dockerignore` их НЕ исключает (сказано там же в комментарии), а `artifacts` в
`pyproject.toml` заставляет hatchling класть их в колесо — по умолчанию он
выбрасывает всё, что игнорирует VCS, а промпты как раз в `.gitignore`.

## 5. Секреты: выпустить заново и заполнить `.env` **[только на сервере]**

Момент выбран не случайно: сервер уже готов, промпты на месте, впереди только
сборка и старт. Отзыв токена, сделанный раньше, оплачивался бы простоем бота на
всё время подготовки.

### 5.1. Новый токен бота

@BotFather → `/mybots` → нужный бот → **API Token** → **Revoke current token**.
Полученную строку сразу вписать в `.env` (ниже) — второй раз она не показывается
из этого экрана без нового отзыва.

> **Отзыв необратим и действует мгновенно.** Старый токен умирает в ту же
> секунду: локальный бот на Маке замолкает сам, и бот не отвечает игрокам с этой
> минуты до конца §8. Вернуться к старому токену нельзя — можно только выпустить
> следующий. Если пауза в работе бота нежелательна, отзыв делается в заранее
> выбранное окно, а не «между делом».

### 5.2. Новый ключ провайдера

В консоли провайдера выпустить ключ **для сервера** и вписать его в `.env`. Тут
порядок мягче: новый ключ можно выпустить, не отзывая старый, — тогда рабочая
машина продолжает работать, а старый ключ отзывается после того, как сервер
подтверждённо считает первую руку. Заодно выставить бюджетный лимит на ключе
(§10: это единственное, что ограничивает именно деньги).

### 5.3. Заполнить `.env`

```bash
cd /srv/poker-harness
cp .env.example .env
chmod 600 .env
openssl rand -hex 24          # пароль Postgres: только hex-символы, см. ниже
nano .env
```

Заполняются все НЕзакомментированные строки; закомментированная строка означает
«необязательно», и раскомментировать её значит задать значение (правило и его
причина — в шапке `.env.example`).

| Переменная | Значение |
|---|---|
| `PG_PASSWORD` | вывод `openssl rand -hex 24`. **Только буквы, цифры, `_`, `-`**: пароль подставляется сырым в URL, и `%`, `&`, `@`, `/`, `:`, `?`, `#` там читаются как разметка — Postgres получит не тот пароль (найдено на живом запуске 2026-09-05) |
| `TELEGRAM_TOKEN` | токен из §5.1 — **новый**, не тот, что на Маке |
| `ANTHROPIC_API_KEY` | ключ из §5.2 — **новый** |
| `LLM_VISION_MODEL`, `LLM_VERDICT_MODEL` | строки вида `"<провайдер>:<модель>"`; берутся с рабочей машины — выбор модели это решение владельца, а не деплоя |
| `LLM_MAX_CONCURRENCY` | `4` — обоснование в §10 |
| `LLM_MAX_PER_MINUTE` | `20` — обоснование в §10 |
| `#OWNER_TG_USER_ID` | ваш id в Телеграме — одноразовый вход владельца на пустую базу; как узнать число и что оно делает — §5.4. Не задан: войти не сможет никто, включая вас |
| `#LLM_VISION_FALLBACK_MODEL` | раскомментировать, если вторая ступень каскада зрения нужна. Решение владельца, а не деплоя: §10 показывает цену (она стоит почти столько же, сколько все первые чтения) и не рекомендует ни включить, ни выключить |
| `#WORKER_CONCURRENCY` | не трогать: дефолт 4 |

**Пароль Postgres фиксируется в момент создания тома.** `POSTGRES_PASSWORD`
действует только при инициализации пустого `pgdata`; смена строки в `.env` после
первого старта не меняет пароль в базе — получится `password authentication
failed`. Менять пароль после первого запуска — только через `ALTER USER` внутри
базы плюс правку `.env`.

### 5.4. Свой Telegram-id: первый вход владельца

**На чистой базе войти в продукт не может никто, и обойти это нечем, кроме этого
шага.** Вход закрыт инвайтом, коды выпускает `/invite` — команда игрока с
`players.is_dev`, а в пустой таблице такого игрока нет. Поэтому в `.env`
дописывается ваш собственный id в Телеграме: `/start` от него заводит ПЕРВОГО
игрока с `is_dev`, без кода.

Узнать id можно тем же токеном, который уже лежит в `.env`. Сначала — в
Телеграме открыть своего бота и отправить `/start` (ответа не будет: бот ещё не
запущен, §8 впереди). Затем на сервере:

```bash
cd /srv/poker-harness
set -a; . ./.env; set +a
curl -s "https://api.telegram.org/bot${TELEGRAM_TOKEN}/getUpdates" | head -c 400; echo
unset TELEGRAM_TOKEN
```

Ожидается JSON, внутри которого есть `"from":{"id":123456789,"is_bot":false,` —
это число и есть ваш id. Токен в историю оболочки не попадает: в самой команде
его нет (тот же приём, что в пункте 2 чеклиста §9).

`{"ok":true,"result":[]}` означает, что сообщение либо ещё не дошло (повторить
через несколько секунд), либо его уже забрал процесс с тем же токеном:
`getUpdates` отдаёт апдейт один раз. Второе возможно, если бот уже запущен, —
тогда `docker compose stop bot`, отправить `/start` ещё раз и повторить команду.

```bash
nano .env     # раскомментировать строку и вписать число: OWNER_TG_USER_ID=123456789
```

Что важно знать про эту переменную, чтобы не искать ответы в коде:

- она действует, **только пока таблица `players` пуста**. Как только в ней
  появилась первая строка (в том числе ваша), переменная не значит ничего:
  постоянной дверью она не становится, и забытая в `.env` строка доступом не
  является;
- второму человеку код нужен по-прежнему — его выпускает `/invite`;
- не задана — вход закрыт всем без исключения; это исходное поведение и
  безопасное умолчание, а не поломка;
- задана не числом — бот не стартует и назовёт переменную одной строкой;
- срабатывание видно в логе: `docker compose logs bot | grep owner_bootstrapped`.

Отправленный сейчас `/start` останется в очереди апдейтов Телеграма (`getUpdates`
без `offset` их не подтверждает), поэтому бот обработает его сразу после
`docker compose up -d` — ответ «Вы вошли как владелец…» может прийти ещё до того,
как вы нажмёте `/start` второй раз. Это ожидаемо, а не второй вход: на второй
`/start` владелец получает уже обычное приветствие.

## 6. Сборка образа **[только на сервере]**

```bash
docker compose build
```

Последняя строка — `naming to docker.io/library/poker-harness:local done`.
На amd64-хосте эмуляции нет, и сборка должна быть заметно быстрее, чем на Маке.

Сразу после сборки — две проверки самого образа, обе дёшевы и обе ловят ровно те
отказы, которые иначе всплывут в середине разговора с игроком:

```bash
# 1. Промпты внутри образа (а не только на диске сервера). Промптов ТРИ, и
#    читают их три разных модуля — проверять надо все три: образ без одного
#    только `tournament.md` прошёл бы проверку по двум и упал бы на первой же
#    сводке турнира.
docker compose run --rm --no-deps bot python -c \
"from harness.parsers.vision_adapter import read_prompt as v; \
from harness.explanation.verdict_text import read_prompt as r, _PROMPT_PATH as VP; \
from harness.explanation.tournament_text import _PROMPT_PATH as TP; \
print('vision', len(v()), '| verdict', len(r(VP)), '| tournament', len(r(TP)))"
```

Ожидается строка с тремя ненулевыми числами (локально — `vision 7080 | verdict
2189 | tournament 1844`; числа зависят от текста промптов). Если вместо неё
трассировка с `PromptUnavailable: нет файла промпта ...` — промпты не доехали до
сборки: вернуться к §4 и пересобрать.

```bash
# 2. Системная cairo и numpy в рантайм-стадии
docker compose run --rm --no-deps bot python -c \
"from ctypes.util import find_library; import numpy, cairosvg; \
print(find_library('cairo'), numpy.__version__)"
```

Ожидается `libcairo.so.2 2.5.2` [проверено локально]. `None` вместо
`libcairo.so.2` означает, что картинка матрицы диапазонов упадёт в проде, а не на
сборке.

## 7. Миграции **[только на сервере]**

Отдельный одноразовый шаг; entrypoint'ы бота и воркера миграций не катят
намеренно (иначе `--scale worker=N` дал бы гонку N контейнеров за одну схему).

```bash
docker compose run --rm migrate
```

На пустой базе ожидается цепочка `0001 → head` — по одной строке
`Running upgrade` на каждую ревизию, начиная с `Running upgrade  -> 0001`
[проверено локально: на пустой базе и на базе, стоящей на 0002]. Сколько их
всего, зависит от того, сколько ревизий в репозитории на момент деплоя, и это не
то, что стоит сверять с документом. Сверять надо с самим репозиторием:

```bash
docker compose run --rm --no-deps migrate alembic heads
docker compose exec -T postgres psql -U harness -d harness -tAc 'select version_num from alembic_version'
```

Оба вывода обязаны совпасть — это и есть проверка. Конкретное число здесь
намеренно не названо: пока писался этот файл, `head` успел сместиться с `0004` на
`0005`. Число в документе стареет, сверка двух команд — нет.

## 8. Старт **[только на сервере]**

```bash
docker compose up -d
docker compose ps
```

Ожидается:

```
NAME                       SERVICE    STATUS
poker-harness-postgres-1   postgres   Up (healthy)
poker-harness-bot-1        bot        Up
poker-harness-worker-1     worker     Up
```

Healthcheck есть только у Postgres, и он не мониторинг, а условие старта: по нему
ждут и миграции, и приложения. У бота и воркера healthcheck'а нет — их живость
проверяется снаружи (§9).

**`restart: unless-stopped` стоит у всех трёх сервисов** (проверяется чтением
`docker-compose.yml`). Что это значит на практике:

- упавший воркер поднимется сам, а начатая задача не потеряется: строка остаётся
  заблокированной, и `reap()` вернёт её в очередь по истечении аренды;
- контейнер, остановленный руками (`docker compose stop`), сам не поднимется —
  в этом весь смысл `unless-stopped`;
- процесс с неполным `.env` будет перезапускаться, повторяя одну и ту же строку
  об отсутствующей переменной. Это одна ошибка в цикле, а не каскад разных;
- поведение после перезагрузки VPS (поднимутся ли контейнеры без человека)
  зависит от того, включён ли `docker.service` в systemd, — **проверить на
  сервере**, пункт чеклиста §9.

## 9. Чеклист первого запуска: что проверяется ТОЛЬКО на сервере

Ни один пункт этого списка не проверен: до сих пор всё жило на Маке под
эмуляцией. Проходить по порядку, записывая фактический вывод, — он же станет
эталоном для следующего деплоя.

| # | Проверка | Команда | Ожидается |
|---|---|---|---|

## 10. Лимиты и деньги

### Что рекомендовано на старте

```
LLM_MAX_CONCURRENCY=4
LLM_MAX_PER_MINUTE=20
```

### Откуда эти числа

Замер — журнал `llm_calls` за 2026-09-06 (ручное тестирование зрения владельцем,
137 вызовов, $4.93). Разбивка по назначениям:

| Назначение | Модель | Успешных | Стоимость | За вызов | Латентность |
|---|---|---|---|---|---|
| `vision_extract` | Sonnet-класс | 88 | $2.4707 | $0.028 | ~10.7с |
| `vision_extract_fallback` | Opus-класс | 31 | $2.2286 | $0.072 | ~12.9с |
| `verdict_text` | Opus-класс | 10 | $0.2337 | $0.023 | ~10.0с |

Отсюда три числа, на которых держатся рекомендации:

1. **35% чтений уходят на вторую ступень** (31 из 88). Средний экран стоит
   $0.028 + 0.35 × $0.072 = **$0.053** вместо $0.028 — каскад почти удваивает
   цену чтения. Это не аргумент его выключить (он ловит несошедшуюся
   контрольную сумму), но это то, что владелец должен знать, включая его.
2. **Латентность вызова 10–13 секунд.** Значит, один воркер физически не может
   выдать больше `4 × 60/11 ≈ 22` вызовов в минуту.
3. **Пиковая наблюдённая минута — 9 вызовов** (один человек, ручные пачки).

**`LLM_MAX_CONCURRENCY=4`** — это потолок одного контейнера воркера:
`WORKER_CONCURRENCY` по умолчанию 4 корутины, каждая ведёт одну задачу и не
зовёт модель дважды одновременно. Больше четырёх один контейнер всё равно не
выберет, меньше — сознательное торможение. Лимит считается в Postgres и общий на
всю систему, поэтому при `--scale worker=2` он не удвоится: четыре останутся
четырьмя (это и есть его смысл).

**`LLM_MAX_PER_MINUTE=20`** — предохранитель, стоящий вплотную к физическому
потолку одного воркера (22/мин). Нормальная работа его не задевает: пик замера
вдвое ниже. Сработает он ровно там, где нужен: вторая реплика, цикл ретраев,
внезапно подешевевшая по латентности модель. Расход при упёршемся в лимит
потоке — 20 × 60 = 1200 вызовов в час, и цена этого часа зависит от того, по
каким моделям он разложится:

- **ожидаемо, на замеренном составе вызовов** ($0.038 — средняя цена вызова,
  $4.933 на 129 удачных): ≈ **$46/час**;
- **в худшем случае**, если весь поток уйдёт на дорогую вторую ступень
  ($0.072 за вызов): ≈ **$86/час**.

Второе число и есть верхняя граница; первое — то, что увидишь при обычном
раскладе. Оба видны на счёте провайдера в тот же час, а не в конце месяца.

Альтернативы, если нужно другое равновесие:

- **10/мин** — вдвое более жёсткий денежный предохранитель (≈$23/час ожидаемо,
  ≈$43/час в худшем случае), но он начнёт тормозить реальные пачки: замеренный
  пик 9/мин упирается в него почти вплотную;
- **30/мин** — воркер не тормозится никогда, но и предохранителя фактически нет
  до появления второй реплики. Сейчас в `.env` на Маке стоит именно `2`/`30` —
  это значения ручного тестирования, а не расчёт.

**Настоящий денежный предохранитель — не здесь.** `LLM_MAX_PER_MINUTE`
ограничивает темп, а не сумму; лимит расхода на стороне провайдера (месячный
бюджет на ключе) — единственное, что ограничивает именно деньги. Выставить его
вместе с выпуском нового ключа.

### Как пересчитать через неделю работы

```sql
-- расход и латентность по назначениям
select purpose, status, count(*), round(sum(cost), 4) as cost, round(avg(latency_ms)) as lat_ms
from llm_calls
where started_at > now() - interval '7 days'
group by 1, 2 order by 1, 2;

-- доля второй ступени каскада (то самое «35%»)
select round(100.0 * count(*) filter (where purpose = 'vision_extract_fallback')
           / nullif(count(*) filter (where purpose = 'vision_extract'), 0), 1) as escalation_pct
from llm_calls where status = 'ok';

-- пиковые минуты: упираемся ли в LLM_MAX_PER_MINUTE
select date_trunc('minute', started_at) as m, count(*)
from llm_calls group by 1 order by 2 desc limit 5;
```

Если пиковая минута регулярно равна лимиту — лимит стал бутылочным горлышком, а
не предохранителем. Если доля второй ступени заметно выше 35% — дорожает каждый
экран, и это вопрос к промпту первой ступени, а не к лимитам.

## 11. Бэкап и восстановление

### Бэкап [проверено локально на живой базе и на выброшенной]

Ночной `pg_dump` строкой в cron (`crontab -e` от пользователя `harness`; `%` в
cron экранируется):

```cron
0 4 * * * cd /srv/poker-harness && docker compose exec -T postgres pg_dump -U harness harness | gzip > /var/backups/harness-$(date +\%F).sql.gz
```

Каталог `/var/backups` должен быть доступен пользователю `harness` на запись
(`sudo install -d -o harness -g harness /var/backups`), иначе cron будет молча
писать в никуда. Проверить руками один раз, не дожидаясь ночи:

```bash
docker compose exec -T postgres pg_dump -U harness harness | gzip > /var/backups/proba.sql.gz
gunzip -c /var/backups/proba.sql.gz | grep -c 'CREATE TABLE'   # не ноль (13 на схеме 0004)
```

Том `hh_files` в бэкап не входит намеренно: разобранные руки лежат в БД, а
исходный файл нужен только для повторного скана. Если нужен и он:

```bash
docker run --rm -v poker-harness_hh_files:/data -v /var/backups:/out alpine tar czf /out/hh.tgz /data
```

### Восстановление [проверено локально на выброшенном проекте]

Разрушающая операция: сначала останавливаются приложения, потом база
пересоздаётся пустой, потом в неё льётся дамп.

```bash
cd /srv/poker-harness
docker compose stop bot worker
docker compose exec -T postgres psql -U harness -d postgres \
  -c 'DROP DATABASE harness WITH (FORCE);' -c 'CREATE DATABASE harness OWNER harness;'
gunzip -c /var/backups/harness-<дата>.sql.gz \
  | docker compose exec -T postgres psql -U harness -d harness -q -v ON_ERROR_STOP=1
docker compose exec -T postgres psql -U harness -d harness -tAc 'select version_num from alembic_version'
docker compose up -d
```

Предпоследняя команда — `select version_num from alembic_version` — должна
напечатать ту же ревизию, что стояла на момент дампа; `up -d` после неё просто
возвращает приложения в работу.
`ON_ERROR_STOP=1` обязателен: без него `psql` доедет до конца, напечатав ошибки в
поток, и «восстановление» закончится наполовину залитой базой с нулевым кодом
возврата.

## 12. Обновление и откат

### Обновление

```bash
cd /srv/poker-harness
git pull --ff-only
docker compose build
docker compose run --rm migrate
docker compose up -d
```

Тот же порядок, что и при первом запуске, и он не случаен: собрать → накатить
схему → поднять. `docker compose up -d` пересоздаст только те контейнеры, чей
образ изменился.

`git pull` промпты **не трогает** — они не в гите; но если промпт менялся на
рабочей машине, его нужно доставить (§4) до `build`.

Перед обновлением, меняющим схему, — бэкап (§11). Он бесплатен и делает откат
возможным.

### Откат

```bash
git checkout <прежний коммит>
docker compose build
docker compose up -d
```

**Если между версиями была миграция, одного отката кода мало.** Сначала
`docker compose run --rm --no-deps migrate alembic downgrade <ревизия>`, и это не
безобидная операция: `downgrade` роняет то, что миграция добавила. Например,
откат 0003 удаляет столбец `players.gg_nickname` вместе с данными. Механика
проверена локально (`0004 → 0002 → 0004` проходит), цена — нет: данных в тестовой
базе не было.

Отката без потерь для «схема ушла вперёд, а данные уже пишутся» не существует —
поэтому бэкап до обновления.

## 13. Диагностика по симптому

Все сообщения ниже воспроизведены в собранном образе [проверено локально], кроме
помеченных отдельно.

| Что видно | Что это | Что делать |
|---|---|---|
| `обязательная переменная окружения LLM_VISION_MODEL не задана; заполните .env, образец — .env.example` | пустая или отсутствующая строка в `.env` | заполнить; трассировки не будет, это не баг |
| `переменная окружения LLM_MAX_CONCURRENCY должна быть целым числом, а не 'четыре'` | мусор в числовой переменной | исправить значение |
| `aiogram.exceptions.TelegramUnauthorizedError: Telegram server says - Unauthorized: invalid token specified` | токен неверен или отозван | взять актуальный токен у BotFather |
| `PromptUnavailable: нет файла промпта /app/.venv/.../prompts/vision.md` | образ собран без промптов | §4, затем `docker compose build` заново |
| `password authentication failed for user "harness"` | `PG_PASSWORD` изменился после создания тома | вернуть прежний пароль либо `ALTER USER` внутри базы |
| Логи воркера пусты, контейнер `Up` | нормальное состояние: воркер молчит, пока нет задач | живость проверяется задачей, доехавшей до `done`, а не логом |
| Первый скан на свежей базе заметно дольше следующих | холодный `calc_cache` (он в Postgres, а не в образе) | ожидаемо, не зависание |
| На `/start` бот отвечает «Пока я работаю по приглашениям», а в `players` пусто | `OWNER_TG_USER_ID` не задан, задан пустым или задан не вашим id | §5.4; переменная действует только на пустой таблице `players`, и после первого вошедшего вход открывается только инвайтом |
| `TelegramConflictError` / «terminated by other getUpdates request» | два процесса с одним токеном (Мак и сервер) | остановить локального бота; **сообщение не воспроизводилось, ожидаемое** |

Общие команды:

```bash
docker compose logs -f bot worker     # JSON structlog, по строке на событие
docker compose ps                     # что поднято и здорово ли

# очередь: что за задачи и чем кончились
docker compose exec -T postgres psql -U harness -d harness -c \
"select id, type, status, attempts, finished_at from jobs order by id desc limit 10;"

# текст ошибки: он не в jobs, а в трейсе — по спану, на котором разбор упал
docker compose exec -T postgres psql -U harness -d harness -c \
"select t.job_id, s->>'name' as span, left(s->>'error', 120) as error \
 from traces t, jsonb_array_elements(t.spans) s \
 where s ? 'error' order by t.job_id desc limit 10;"
```

Столбца с ошибкой в `jobs` нет — это не упущение диагностики, а устройство:
причина падения живёт в `traces.spans`, рядом со станцией, на которой разбор
кончился. Оба запроса выполнены на живой базе [проверено локально].

`docker compose down` останавливает всё, не трогая данные. `docker compose down
-v` **удаляет тома** — и базу, и присланные игроками файлы; на сервере это
делается только осознанно и после бэкапа.

## Приложение: локальный режим на Маке

Полностью контейнерный запуск на Маке невозможен по времени: под эмуляцией
amd64 счёт эквити идёт на порядки медленнее, и воркер не укладывается в дедлайн
задачи (480с при 1.7с нативно). Поэтому на Маке воркер запускается **нативно**,
а в контейнере остаётся только Postgres. Как именно — в README, раздел «Локальный
режим на Маке (не деплой)». На сервере ничего этого не нужно: там amd64 и
эмуляции нет.
