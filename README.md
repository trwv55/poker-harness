# poker-harness

Разбор покерных рук с **проверенным расчётом**: движок правил пересчитывает и валидирует
каждую руку, математику считает код, LLM только излагает результат словами. Турнирный
NLHE (MTT с анте), рум GG (PokerCraft). В разработке.

## Состояние

Конвейер собран целиком — от присланного файла hand history до сообщения игроку:

```
HH-файл → HHParser → HandNormalizer → Hand engine (PokerKit + валидатор) → EnrichedHand
        → аналитическое ядро (эквити, ICM, пуш-фолд, шансы банка) → скан руки → бот
```

На двух реальных турнирах (318 рук) конвейер даёт вердикт `pass` на всех руках,
пересчитанный банк совпадает с записью рума, сохранение фишек и структура сайд-потов
сходятся. Аналитическое ядро существует и покрыто тестами; вокруг него стоит
инфраструктура: очередь задач в Postgres, воркер со станциями и трейсом, лимитер
провайдер-слоя, телеграм-бот с сессиями и квотой.

Оба места, где в этой системе вообще живёт модель, теперь есть в коде: разбор
скриншота (`src/harness/parsers/`, зрение с каскадом из двух ступеней) и словесный
вердикт (`src/harness/explanation/`). Промпты к ним в репозиторий не входят —
см. «Публикация» ниже; без них код импортируется, а первый вызов модели падает
громко и с именем файла.

**Живая приёмка была одна, и не на сервере.** 2026-09-06 бот принял настоящий файл
турнира от игрока, воркер досчитал скан и доставил сводку — но происходило это на
Маке, где воркер запускался нативно, потому что под эмуляцией amd64 счёт эквити не
укладывался в дедлайн задачи («Локальный режим на Маке» ниже). Зрение проверялось
владельцем вручную на реальных скриншотах, автоматического живого гейта у него нет
по решению владельца.

**Ни один настоящий amd64-хост образ не запускал** (подробности — в «Архитектурном
ограничении образа» ниже). Всё, что ниже описано про деплой, описывает устройство и
проверки в эмуляции, а не опыт эксплуатации; пошаговый первый запуск на чистом
сервере — [docs/deploy-runbook.md](docs/deploy-runbook.md).

## Разработка

```bash
uv sync
uv run pytest -q -ra
uv run ruff check . && uv run pyright
```

Картинка матрицы диапазонов (`explanation/range_render.py`) рисуется через
`cairosvg`, а он грузит СИСТЕМНУЮ библиотеку cairo — колесо её не содержит. В
образе стоит пакет `libcairo2` (Dockerfile), на macOS достаточно
`brew install cairo`; путь к каталогу Homebrew модуль дописывает сам.

### Evals — отдельный этаж, руками и за деньги

Тесты проверяют код, evals проверяют модель ([`.claude/EVALS.md`](.claude/EVALS.md)).
В `pytest` они не входят и в CI не гоняются; прогон верности изложения вердикта —
обязателен при смене `LLM_VERDICT_MODEL` или промпта вердикта:

```bash
# синтетические кейсы из evals/verdict/cases (в репозитории)
uv run python -m harness.platform.eval_runner verdict
# те же проверки на настоящих раздачах с диска
uv run python -m harness.platform.eval_runner verdict --hh fixtures/hh/<файл>.txt --hands 3
```

Прогон ходит к настоящей модели через тот же провайдер-слой, что и прод, поэтому ему
нужны ключ провайдера и `DATABASE_URL` (строка `llm_calls` пишется на каждый вызов —
из неё же берётся стоимость прогона, которую печатает раннер).

### Публикация

Репозиторий открыт до выхода продукта. Что в него не попадает и почему — в
[docs/publishing-policy.md](docs/publishing-policy.md); правило проверяется хуком
`pre-push`, который включается на клоне один раз:

```bash
git config core.hooksPath .githooks
```

### Фикстуры

Регрессионная сетка гоняется на реальных hand history — это приватные данные игрока,
и в репозиторий они не входят. Без файлов в `fixtures/hh/` тесты, зависящие от них,
**пропускаются**, о чём прогон сообщает явно (`-ra`).

Это значит: **зелёный CI не равен проверенному конвейеру.** Полный гейт на 318 руках
выполняется только локально, там где файлы есть. Чтобы его включить, положите
экспортированные из PokerCraft файлы турниров в `fixtures/hh/` под именами
`daily-classic-146.txt` и `pko-bounty-172.txt` (числа в именах — количество рук,
которое ожидает сетка).

## Деплой

Docker Compose на VPS: `postgres`, `bot`, `worker` (спека §12). Все три процесса
собираются в один образ (`Dockerfile`), различает их команда сервиса, — так бот,
записавший файл, и воркер, читающий его, гарантированно одной версии.

Здесь — устройство. Пошаговый первый запуск на чистом Ubuntu LTS, с ожидаемым
выводом каждой команды, ротацией секретов, чеклистом того, что проверяется только
на сервере, и рекомендованными значениями лимитов —
[docs/deploy-runbook.md](docs/deploy-runbook.md).

Перед первым запуском:

```bash
cp .env.example .env   # заполнить: пароль БД, токен бота, модели, лимиты
```

Заполняются все строки, которые в шаблоне **не** закомментированы: пустое
значение для них — это ошибка старта с явным сообщением, а не «возьмём дефолт».
Закомментированные строки (вторая ступень каскада зрения, `WORKER_CONCURRENCY`) —
необязательные; раскомментировать значит задать. Пустая строка `ИМЯ=` в `.env`
не равна отсутствию переменной: Compose передаёт её как пустое значение, поэтому
необязательные переменные и лежат в шаблоне закомментированными.

Одно исключение из этого правила названо в самом шаблоне: ключ провайдера
(`ANTHROPIC_API_KEY`) обязателен, но его читает не наш код, а библиотека, —
поэтому пустое значение роняет не старт, а первый вызов модели.

**Токен бота и ключ провайдера на сервере обязаны быть новыми.** Старый токен
уехал в логи и в `traces` на приёмке 2026-09-05 (починено в `f775d06`, записи в
базе вычищены), и деплой — естественный момент выпустить оба секрета заново.

`.env` в репозиторий не едет никогда (`.gitignore` + pre-push хук). В образ он
тоже не попадает: переменные приходят в контейнер окружением, а не файлом внутри.

### Приватные файлы: промпты моделей

Клон репозитория **не содержит промптов** — ни зрения
(`src/harness/parsers/prompts/`), ни изложения
(`src/harness/explanation/prompts/`): оба каталога закрыты политикой публикации.
Без них процессы стартуют, HH-скан считается целиком, а первый вызов модели
падает `PromptUnavailable` с именем недостающего файла.

Поэтому у деплоя есть шаг, которого нет ни в одной команде ниже: привезти
промпты на сервер (`rsync` с рабочей машины) **до** `docker compose build`.
Образ забирает их из рабочего дерева тем же `COPY src ./src`, что и код, — то
есть собранный без промптов образ доставкой файлов на диск не чинится, нужна
пересборка. По той же причине изменение промпта требует пересборки образа.

Что промпты доедут до образа, держат два конца, оба проверяемые: `.dockerignore`
их не исключает, а `artifacts` в `pyproject.toml` кладёт их в колесо (по
умолчанию hatchling выбрасывает всё, что игнорирует VCS, — а промпты в
`.gitignore`). Команды доставки и проверки — в
[runbook'е](docs/deploy-runbook.md), §4.

### Порядок

```bash
# промпты уже на месте (см. выше)
docker compose build && docker compose run --rm migrate && docker compose up -d
```

`alembic upgrade head` на пустой базе накатывает цепочку `0001 → 0004` (проверено
на пустой базе и на базе, стоящей на 0002; ревизии идемпотентны при повторном
прогоне). Сверять после наката имеет смысл не с числом в документе, а с
репозиторием: `alembic heads` и `select version_num from alembic_version` обязаны
совпасть.

Масштабирование воркера (прочитайте сначала «Про `--scale`» ниже):

```bash
docker compose up -d --scale worker=2
```

Тот же порядок — на каждом обновлении: собрать, накатить миграции, поднять.

**Миграции — отдельный одноразовый шаг, и это не стиль, а требование.**
Entrypoint'ы `bot` и `worker` миграций **не катят**: иначе `--scale worker=N` дал бы
гонку N контейнеров за одну схему. Сервис `migrate` объявлен с
`profiles: ["tools"]` — он не стартует вместе с `up` и живёт ровно один прогон
`alembic upgrade head`, после чего контейнер удаляется (`--rm`).

### Тома и файлы игрока

| Том | Что внутри | Кто монтирует |
|---|---|---|
| `pgdata` | база: руки, сессии, задачи, трейсы | `postgres` |
| `hh_files` | присланные игроками hand history, `DATA_DIR/hh/{sha256}.txt` | `bot` **и** `worker`, оба в `/data` |

Второй том общий не для удобства: бот сохраняет файл и кладёт **абсолютный** путь
в задачу, воркер открывает файл ровно по этому пути — контейнеры разные, поэтому
и том, и точка монтирования у них обязаны совпадать. Держит это именно пара
«общий том + одинаковая точка монтирования»: переменную `DATA_DIR` читает только
бот (воркер получает готовый путь из задачи), у воркера она задана защитно.

> **Точку монтирования `/data` нельзя поменять после первого запуска.** Путь
> уходит в `jobs.payload.source_file` и `tournaments.source_file`, и по нему же
> различаются повторные загрузки. Смена пути осиротит все старые строки и
> заставит повторную загрузку завести второй турнир на тот же файл. Менять —
> только вместе с миграцией, переписывающей оба столбца.

Том **именованный**, а не `./data` из рабочего дерева: внутри — сырые руки живых
людей, и репозиторий для них запрещённое место (`docs/publishing-policy.md`).

### Бэкап

Ночной `pg_dump` строкой в cron (`crontab -e` на VPS; `%` в cron экранируется):

```cron
0 4 * * * cd /srv/poker-harness && docker compose exec -T postgres pg_dump -U harness harness | gzip > /var/backups/harness-$(date +\%F).sql.gz
```

Том `hh_files` в бэкап не входит намеренно: разобранные руки лежат в БД, а
исходный файл нужен только для повторного скана. Если нужен и он —
`docker run --rm -v poker-harness_hh_files:/data -v /var/backups:/out alpine tar czf /out/hh.tgz /data`.

Команда `pg_dump` выше выполнена на живой базе проекта (схема 0004, 13 таблиц в
дампе) — она работает как написана. **Восстановление** — операция разрушающая и
одной командой не описывается: приложения останавливаются, база пересоздаётся
пустой, дамп льётся с `-v ON_ERROR_STOP=1` (без него `psql` доедет до конца,
напечатав ошибки, и вернёт ноль на наполовину восстановленной базе).
Последовательность целиком, проверенная на выброшенной базе, — в
[runbook'е](docs/deploy-runbook.md), §11.

### Healthcheck, рестарты и логи

`restart: unless-stopped` стоит у всех трёх сервисов. Что из этого следует:

- упавший процесс поднимается сам; начатая воркером задача при этом не теряется —
  строка остаётся заблокированной, и `reap()` возвращает её в очередь по
  истечении аренды (спека §8.1);
- контейнер, остановленный руками, сам не поднимается — в этом смысл
  `unless-stopped`, а не `always`;
- процесс с неполным `.env` перезапускается, повторяя одну и ту же строку об
  отсутствующей переменной: это одна ошибка в цикле, а не каскад разных;
- поднимутся ли контейнеры после перезагрузки VPS — зависит от того, включён ли
  `docker.service`; **не проверено нигде**, это пункт чеклиста первого запуска.

Healthcheck в проекте один — у `postgres`, и он не мониторинг, а условие старта:
по нему ждут и миграции, и приложения (без него `alembic upgrade head` стучится в
ещё не поднявшийся Postgres). У `bot` и `worker` healthcheck'а нет сознательно: у
них нет ни порта, ни эндпоинта, а проверка «процесс жив» отвечала бы на вопрос, на
который уже отвечает Docker. Их живость проверяется снаружи — `getMe` и ответ на
`/start` у бота, доехавшая до `done` задача у воркера.

Логи ограничены на уровне compose: 10 МБ на файл, 5 файлов на контейнер. Драйвер
`json-file` по умолчанию не ротирует ничего, а это на сервере означает и
заполненный диск, и вечно живущую строку лога — в которую однажды уже уехал токен
бота. Ограничение применяется при пересоздании контейнера (`up -d`), а не на лету:
у контейнера, созданного раньше, `docker inspect` покажет пустую конфигурацию
логов.

### Про `--scale worker=2`

`WORKER_CONCURRENCY` — число **корутин** одного контейнера. Тяжёлый счёт при этом
уходит в процессный пул размером `os.cpu_count()`, то есть по числу ядер **хоста**:
cgroup-лимит `cpus:` этого числа не меняет. Значит, на VPS с 2–4 vCPU вторая
реплика не удваивает пропускную способность — она удваивает число процессов,
конкурирующих за те же ядра, и удваивает память. Реплики оправданы, когда
добавлены ядра или воркеры разъезжаются по хостам; в остальных случаях крутится
`WORKER_CONCURRENCY`. Подробный разбор — в комментарии к сервису `worker` в
`docker-compose.yml`.

Корректности `--scale` при этом не мешает ничто: `worker_id` уникален между
репликами (hostname + PID), лимиты провайдер-слоя считаются в Postgres и на N не
умножаются, задачи разбираются `FOR UPDATE SKIP LOCKED`.

### Диагностика

```bash
docker compose logs -f bot worker     # JSON structlog, по строке на событие
docker compose ps                     # что поднято и здорово ли
```

Пустые логи воркера при статусе `Up` — нормальное состояние: пока задач нет, он
молчит. Текста ошибки в `jobs` нет: причина падения лежит в `traces.spans`, рядом
со станцией, на которой разбор кончился. Запросы к очереди и к трейсу — в
[runbook'е](docs/deploy-runbook.md), §13, там же таблица «симптом → причина» с
дословными сообщениями.

Процесс без нужной переменной окружения не стартует и говорит одной строкой,
какой именно переменной не хватает, — трассировки в этом случае не будет. Из-за
`restart: unless-stopped` контейнер с неполным конфигом будет перезапускаться,
повторяя ровно ту же строку: это одна и та же ошибка, а не каскад разных.

Первый скан на свежей базе считается по холодному `calc_cache` (он живёт в
Postgres, а не в образе) и потому идёт заметно дольше последующих — это
ожидаемо, а не зависание.

`docker compose down` останавливает всё, не трогая данные. `docker compose down
-v` **удаляет тома** — и базу, и присланные игроками файлы; на VPS это делается
только осознанно и после бэкапа.

### Архитектурное ограничение образа

Образ собирается и работает **только на linux/amd64**: `eval7` не публикует ни
исходников, ни колёс под `linux/arm64`. Для продакшена берётся amd64-машина.

На arm-хосте всё зависит от того, зарегистрирована ли эмуляция binfmt: на Docker
Desktop (Mac с Apple Silicon) она есть, и те же команды работают — медленно, но
работают; на голом arm64-Linux **без** `qemu-user-static`/`binfmt_misc` те же
команды падают сразу, `exec format error`. То есть «работает, просто медленно» —
свойство машины, а не образа.

**Ни один настоящий amd64-хост этот образ пока не запускал.** Всё, что проверено
(сборка, миграции с нуля и с 0002, старт контейнеров, общий том, промпты внутри
образа, `libcairo2` и numpy, бэкап и восстановление), проверено на arm64-маке
через эмуляцию. Список проверок с командами и выводом — в
[runbook'е](docs/deploy-runbook.md), §14; список того, что проверяется только на
сервере, — там же в §9.

Версия Python в образе запинена точно (3.12), и почему это не косметика — в
шапке `Dockerfile`; CI гоняет гейт на той же версии (`.python-version`).

### Локальный режим на Маке (не деплой)

На Маке проект **не запускается целиком в контейнерах**, и это не предпочтение, а
замер: под эмуляцией amd64 счёт эквити идёт на порядки медленнее, и воркер не
уложился в дедлайн задачи (480 с), тогда как тот же скан нативно считается за
единицы секунд — 1.7 с на холодном замере, 3.9 с на живой приёмке 2026-09-06.
На сервере этой проблемы нет: там amd64 и эмуляции нет вовсе.

Рабочая раскладка на Маке: **Postgres в контейнере, приложения нативно.**

```bash
# 1. Порт базы наружу — override ВНЕ репозитория (в репозиторий он не едет:
#    компоновка деплоя не должна знать про чью-то локальную машину)
cat > ~/poker-harness-local.yml <<'YML'
services:
  postgres:
    ports:
      - "127.0.0.1:5432:5432"
YML
docker compose -f docker-compose.yml -f ~/poker-harness-local.yml up -d postgres

# 2. Миграции — по-прежнему контейнером, чтобы схему катал тот же alembic
docker compose run --rm migrate

# 3. Бот и воркер — нативно, оба с одним DATA_DIR
set -a; . ./.env; set +a
export DATABASE_URL="postgresql+asyncpg://harness:${PG_PASSWORD}@127.0.0.1:5432/harness"
```

**Бот и воркер обязаны быть по одну сторону границы контейнера.** Бот кладёт в
задачу абсолютный путь к сохранённому файлу, воркер открывает ровно его: бот в
контейнере (`DATA_DIR=/data`) плюс нативный воркер дают путь `/data/hh/...`,
которого на Маке не существует. Именно это и случилось на приёмке — путь в задаче
правился руками. Отсюда правило: либо оба в контейнерах (сервер), либо оба
нативно (Мак).

Второе следствие: **токен у бота один.** Запущенный локально бот и бот на сервере
с тем же токеном дерутся за апдейты; после деплоя локальный бот останавливается,
а не «пусть работает».
