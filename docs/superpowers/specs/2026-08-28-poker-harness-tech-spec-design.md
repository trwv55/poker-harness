# Покерный harness — тех-спека (v1.0)

Статус: на ревью. Входные документы: `.claude/ARCHITECTURE.md` (логическая архитектура),
`.claude/EVALS.md` (слой проверок), `.claude/SESSIONS_UX.md` (сессии и продуктовый вход),
`.claude/SCALING.md` (масштабирование и себестоимость), `.claude/poker_harness_services.svg`
(схема сервисов), реальные GG-файлы в `.claude/RawHands/`.

Спека закрывает технологические решения для всей системы и детально прорабатывает первые
ступени порядка разработки (парсер, движок, префлоп-ядро, платформа, HH-путь). Постфлоп-зона
«предполагая» и глубина vision-промптов оставлены на уровне решений — их детализация
происходит на своих шагах реализации, когда появятся данные (spike, телеметрия, evals).

## 2. Топология

Два процесса, один кодовый образ, разные точки входа:

- **`bot`** — aiogram 3. Принимает сообщения, роутит по типу входа (фото / `.txt`-файл /
  текст / кнопки), пишет задачи в `jobs`, обрабатывает меню, ответы на эскалации и кнопки
  под вердиктом. Покерной логики не содержит.
- **`worker`** — цикл по `jobs` (`SELECT … FOR UPDATE SKIP LOCKED`), выполняет конвейер
  целиком: парсер → нормалайзер → движок → ядро → изложение. Прогресс и результаты шлёт
  игроку сам, напрямую через Bot API. Конкурентность: N корутин (конфиг); CPU-нагрузка
  (префлоп-скан) — в `ProcessPoolExecutor`, чтобы не блокировать event loop.

Процессы общаются только через Postgres. Границы по схеме сервисов: `bot` — часть станции 7
(транспорт, сессии, роутер входа), `worker` — станции 1–5, Память и `llm()` — общие.

Масштабирование: `docker compose up --scale worker=N` — SKIP LOCKED разруливает конкуренцию
захвата. Ориентир из SCALING.md: один воркер до первых десятков пользователей, 2–4 — на ~1000.

## 4. Структура репозитория

```
poker-harness/
  src/harness/
    contracts/      # RawHand, CanonicalHand, EnrichedHand, Range, AnalysisResult
    parsers/        # vision_adapter.py (LLM), hh_parser.py (код)
    normalizer/     # RawHand -> CanonicalHand
    engine/         # replay.py (обвязка PokerKit), validation.py
    analysis/       # classifier.py, strict/, assuming/, error_cost.py, tools/
    explanation/    # verdict_text.py (LLM), range_render.py (код)
    presentation/   # шаблоны сообщений игроку, клавиатуры, статус-строка
    memory/         # модели SQLAlchemy, репозитории
    platform/       # llm-фасад + лимитер, jobs-очередь, трейс, eval_runner, конфиг
    bot/            # aiogram: роутер входа, меню, кнопки, эскалации, инвайты, квоты
    worker/         # цикл очереди, оркестрация конвейера, чекпоинты
  tests/            # этаж 1 (см. §10)
  evals/            # этажи 2-4: vision/, verdict/, e2e/ + эталоны
  fixtures/hh/      # реальные GG-файлы (переносятся из .claude/RawHands/)
  scripts/          # spike_vision.py (выкидной, §13) и пр. разовые
  docs/superpowers/specs/
```

Корневой пакет `harness`: пакет верхнего уровня `platform` затенял бы stdlib-модуль
`platform`.

**Правило зависимостей.** Конвейерные пакеты (`contracts`, `parsers`, `normalizer`,
`engine`, `analysis`, `explanation`) не импортируют ни Телеграм, ни БД — все данные им
передаются аргументами, результат возвращается значением. Про инфраструктуру знают только
`bot`, `worker`, `memory`, `platform`. Следствия: конвейер тестируется без инфраструктуры;
«добавить рум = добавить парсер» остаётся правдой.

`vision_adapter` и `verdict_text` зовут LLM только через `platform.llm` (внедряется
аргументом-зависимостью) — единая точка учёта и лимитов не обходится.

**Правило единого голоса.** Все сообщения игроку (тексты, клавиатуры, статус-строка)
собирает только `presentation/`; `bot` и `worker` их отправляют, но не форматируют — оба
процесса пишут игроку, и без единого сборщика стили разъедутся. Граница: `explanation/` —
покерное содержание (что сказать), `presentation/` — вид в Телеграме (как показать);
`presentation/` знает про разметку ТГ, но не про БД и не про LLM.

## 5. Контракты данных

Три pydantic-модели, каждая с `schema_version: int`. Новые поля — только опциональные:
сохранённые руки и eval-датасет читаются любой последующей версией кода.

### 5.1 RawHand — сырьё без интерпретации

Парсер переписывает источник, ничего не выводя и не исправляя.

- `provenance`: `hand_history | screenshot`; `source_ref` (путь/хэш файла или скрина).
- Для скрина: `confidence: dict[field, float]`, `needs_review: list[field]` — валидатор
  будет знать, какое поле переспрашивать; `image_hash` — ключ кэша извлечений.
- Заголовок: `hand_no` (id руки в руме), `tournament_id`, `tournament_name`, `level`,
  `sb`, `bb`, `ante`, `ante_type` (per-player — формат GG), `timestamp`.
- Стол: `table_name`, `max_seats`, `button_seat`.
- Места: `[{seat, label, stack}]` — label: `Hero`, анонимный хэш (HH) или ник (скрин).
- Посты анте и блайндов — построчно, как в источнике.
- Карты: `dealt: dict[label, list[card] | []]` — в HH пустые для чужих; со скрина — что
  прочитал vision.
- Действия: упорядоченный `[{street, label, kind, amount, to_amount?, is_all_in, raw_line}]`
  — `raises X to Y` несёт оба числа; `calls N and is all-in` — N это доплата; `raw_line`
  сохраняется для отладки и текстов эскалаций.
- Доска по улицам; вскрытия (в GG при олине идут до доски — порядок строк сохраняется);
  строки `collected` — как есть, без меток мейн/сайд.
- SUMMARY: `total_pot`, `rake`, GG-поля (`jackpot`, `bingo`, `fortune`, `tax`),
  доска, результаты по местам.
- Только со скрина: ники за столом, суммы баунти, отображаемый банк.

### 5.2 CanonicalHand — единая интерпретация

Выход нормалайзера:

- позиции выведены из баттона (BTN/SB/BB/UTG/…); суммы — int-фишки + дубль в bb;
- семантика ставок унифицирована: каждое действие несёт «итого поставлено на улице после
  действия» — движку не нужно догадываться про доплаты;
- `tournament_id` + `hand_no` — ссылка на турнир с первого дня (закладка архитектуры);
- идентичности: `identity: anon_hash | nick | hero` — от этого зависит право писать заметку;
- `bounties: dict[label, amount] | None` с меткой источника (только vision → зона «строго»;
  из HH невосстановимы → допущение, зона «предполагая»);
- провенанс и confidence проезжают насквозь.

### 5.3 EnrichedHand — плюс рапорт движка

CanonicalHand + результат единственного прогона реплея:

- банк на каждой улице (пересчитанный движком — SUMMARY не является источником истины);
- эффективные стеки и SPR на каждой точке решения; сайд-поты; чей ход в каждой точке;
- флаги физически невозможных действий;
- `validation: pass | escalate(fields, questions) | reject(reason)` — вынесенный вердикт
  политики (§8.3 — как эскалация едет дальше).

### 5.4 Range — частотный формат

`Range` = веса `0.0..1.0` на 169 классов рук (`AKs`, `T9o`, …), опционально — детализация
до 1326 конкретных комбо там, где важны блокеры. Обоснование: равновесные стратегии почти
всегда смешанные («пуш 70%»); бинарный формат — частный случай весов {0,1}, обратное неверно.
Рендер закрашивает клетку долей веса. eval7 принимает взвешенные диапазоны нативно.

### 5.5 AnalysisResult — выход ядра

Список точек решения Hero: `{street, spot, action_taken, best_action, ev_diff_bb,
zone: strict | assuming, assumption?: {range, source: note | archetype | population},
tools_used}` + ранжирование по цене ошибки. Формулировки скана — «расхождение», не «ошибка»
(осознанный эксплойт может быть верным). LLM в ядре нет.

**Правило зоны — по инструменту, не по улице (арх. §4).** `strict` ставится только тогда,
когда вывод не опирается на угаданный диапазон: (а) HU пуш-фолд, где колл-диапазон получен
из равновесия (`nash_hu`, ровно 2 живых игрока); (б) пот-оддсы и эквити против заданного
диапазона; (в) любой спот, где вердикт **устойчив к диапазону** — проверяется
bracket-тестом:
EV пересчитывается против узкой и широкой модели оппонентов, и если лучшее действие совпало,
допущение не несёт нагрузки. Мультивей-шов (3+ живых) равновесия не имеет — колл-диапазоны
игроков позади моделируются, поэтому по умолчанию `assuming` с явным показом допущения;
bracket-тест может повысить конкретную точку до `strict`. **Арифметика EV при этом точная**
(перебор подмножеств коллеров с мультивей-эквити и сайд-потами) — приближение живёт только
в диапазонах, и зона показывает это игроку.

**(г) Постфлоп-перебор** (`river_call`, `turn_flop_call`) — четвёртый случай `strict`, и он
не был предусмотрен этим списком: модели диапазона в нём нет вовсе, есть перебор борда и
доборов. Цены такая точка не получает (`SpotKind.POSTFLOP` вне `JUDGED_SPOTS`, в сумму
потерь и в ранжирование не входит), а лучшее действие называет только ривер с доказанным
фолдом. Отсюда и третье состояние зоны у РУКИ: точка без названной линии её не подписывает,
и статус-строка остаётся без сегмента зоны (`worker.pipeline._hand_zone`).

### 5.6 Блок «Что было» — реплей руки, собранный кодом

Дополнение владельца. У изложения было два выхода — текст вердикта (LLM) и матрица диапазонов
(код). Добавляется третий: **реконструкция хода руки. Кодовый, ноль токенов.**

**Зачем.** Разбор без хода руки нечитаем: читатель не может ни восстановить раздачу, ни проверить
вывод. Конкурент (`feed`, см. docs/market/) выдаёт вердикт без реплея, и его модель тратит токены на
пересказ улиц словами, при этом путаясь — в шапке позиция UTG, в тексте «cold-calling with UTG+1».
Такое противоречие читатель **не может обнаружить**, не имея перед глазами хода руки. Реплей
закрывает и читаемость, и проверяемость.

**Новых расчётов не требуется.** `EnrichedHand` уже содержит всё: действия по улицам в порядке хода,
банк на каждой улице, стеки в каждый момент, эффективные стеки, SPR, точки решения. Цена решения
приходит из `AnalysisResult`, статистика оппонента — из `player_stats_by_label`. Реплей — это
форматированный вывод существующих контрактов.

#### Что изменилось против первой редакции

Первая редакция этого раздела предписывала блок под кнопкой «Подробнее», построчный формат по улицам
и суммы в фишках. Реализация это построила, и по живому продукту стало видно три вещи. Первое:
блок за кнопкой не читает почти никто, а основное сообщение без него выглядит пустым. Второе:
построчный формат по улицам занимает экран телефона целиком ради руки, которая укладывается в две
строки прозой. Третье: суммы в фишках заставляют читателя делить в уме, потому что вердикт ниже
говорит в ББ.

Отдельно фиксируется расхождение, которое было допущено молча и до сих пор не отражено здесь:
первая редакция требовала «отметку точек решения Hero с вердиктом ядра и ценой в bb», а в образце
вывода стояли комбинация на вскрытии и эквити на олл-ине. Реализация всё это отбросила, записав
причину только в докстринг `hand_replay.py`. Цена решения возвращается ниже; комбинация и эквити
не возвращаются, и причина названа явно.

#### Формат

Блок печатается **первым в сообщении разбора**, над точками решения и над текстом модели.
Что остаётся кнопке «Подробнее» — открытая точка внизу раздела.

Шапка — одна строка: позиция героя, карманные карты, стек в ББ. Дальше **ход раздачи прозой,
одним абзацем**: действия через `→`, улицы разделены точкой, борд назван в начале своей улицы,
банк — один раз на улицу. Завершает абзац цена решения.

```
Что было
Вы на CO, J♥️9♥️, 10.0 ББ.
Опен 2 → BB (a1b2c3d4, VPIP 25%) колл. Флоп K♥️J♥️2♥️, банк 5.5. BB чек → вы бет 1.9 → колл.
Тёрн 4♣️ чек-чек. Ривер 6♦️, BB бет 3.1 → вы фолд. Потеря 3.9 ББ.
```

**Правила:**

- **Все суммы в ББ**, с одним знаком после точки. Фишек в блоке нет: вердикт ниже говорит в ББ, и
  два масштаба в одном сообщении заставляют читателя пересчитывать. Приблизительности нет тоже —
  движок считает банк точно, и «~5.5» обещало бы неуверенность, которой у кода нет.
- **Масти обязаны читаться мгновенно: символ плюс цвет** (♠♣ тёмные, ♥♦ красные). Текстовое `Qs 8s`
  не даёт увидеть одномастность так же быстро, как `Q♠ 8♠`, а от этого зависит оценка флеш-дро и
  борда. Никогда не выводить карты в буквенной нотации. За символом стоит селектор
  эмодзи-презентации U+FE0F; каким выйдет цвет, решает шрифт клиента.
- **К герою обращаются на «вы»** — так же, как во всех трёх промптах изложения. Блок и текст под
  ним не имеют права говорить с игроком по-разному.
- **Позиция важнее ника.** Действия называются позицией; ник появляется только у оппонента, о
  котором есть что сказать (см. ниже). Первое действие абзаца называет своего автора наравне с
  остальными: «Опен 2» без позиции читается однозначно только тогда, когда открыл герой.
- **Сумма — это ставка целиком, а не добавка к предыдущей.** `Бет 1.9` значит 1.9 ББ в банке от
  этого игрока на этой улице, и так же читаются рейзы.
- **Однотипные фолды слипаются** (`UTG/HJ фолд`), улицы без действий схлопываются
  (`Тёрн 4♣️ чек-чек`), размер в ББ ставится у каждой суммы.
- **Объём:** префлоп-рука — одна строка прозы, рука с постфлопом — две-три. Длиннее значит формат
  нарушен.
- **Чего не делать:** не выводить стеки всех игроков, не показывать SPR, не давать банк после
  каждого действия, не называть комбинации и не печатать эквити.

#### Оппонент: метка и статистика

Рядом с оппонентом печатается его метка в руме и частоты, если они посчитаны:
`BB (a1b2c3d4, VPIP 25%)`.

**Провенанс решает, есть ли статистика вовсе.** Метка участника сквозная только внутри турнира —
между турнирами комната выдаёт новую (`OpponentsRepo`). Поэтому на входе hand history частоты
считаются по рукам турнира и печатаются, а на входе скриншотом их нет: одна рука не даёт
знаменателя. Блок в этом случае печатается без скобок, а не с нулями.

**Частота без выборки не печатается.** `PlayerStats._share` возвращает `None` при нулевом
знаменателе, и это единственно честное поведение: «VPIP 0%» по нулю раздач — утверждение, которого
никто не измерял. Доступный набор: VPIP, PFR, 3-бет, фолд на к-бет, к-бет флоп, баррель тёрн,
баррель ривер.

**Правило зависимостей не нарушается.** `explanation` не импортирует `memory`: статистика приходит
в реплей аргументом, а добывает её вызывающий (`worker.pipeline`).

#### Чего в блоке нет и почему

- **Комбинация на вскрытии** («пара валетов») и **эквити на олл-ине** — оценка руки, то есть
  расчёт. Эквити к тому же не лежит в `AnalysisResult`: напечатать его значит либо посчитать в
  изложении, либо завести новое поле в ядре. И то и другое — отдельная задача, не эта.
- **Вердикт словами.** Блок говорит, ЧТО было; чего с этим не так — соседние строки разбора и текст
  модели. Цена в ББ при этом печатается: это число ядра, а не суждение.

#### Следствие для промпта вердикта

Раз ход руки показан кодом, **LLM не пересказывает происходившее** — класс ошибок «модель переврала
ход руки» негде совершить.

Но первая редакция сделала из этого лишний вывод: модель не получала ни карт, ни борда, ни позиции
вовсе. Объяснять решение ей было нечем, и текст выходил пересказом собственных цифр («вы сбросили,
шов был лучше, это стоило 3.9 bb»). **Карты, борд и позиция идут в выжимку** — это факты руки, а не
арифметика, и на границу «точное считает код» они не посягают. Туда же идёт **состав допущенного
диапазона**, а не только его доля в процентах: «предполагая, что он отвечает только тузами и
половиной королей» и есть существо пуш-фолд вердикта.

**Следствие для проверки верности.** В названиях рук есть цифры (`A5s`, `T9o`, `99`), и
`unsupported_numbers` прочтёт их как выдуманные величины. Нотация карт перестаёт считаться числом:
карта — не количество. Гнать её через `NumberBook.token` нельзя, это разрешило бы модели писать
«теряет 5 bb» свободно.

**Правило, дополняющее принцип архитектуры:** код показывает, **что было**; LLM объясняет,
**что с этим не так**.

**Размещение в коде — решено:** `explanation/hand_replay.py`. По симметрии с `range_render` (тоже чистый
код, тоже рендер покерного содержания), а `presentation/` собирает из готового реплея сообщение.
Правило «`explanation` — покерное содержание, `presentation` — вид в Телеграме» остаётся
без исключений: у изложения три выхода — текст вердикта (LLM), матрица диапазонов (код)
и реплей руки (код).

#### Открытые точки к ревью владельца

1. **Какие частоты печатать рядом с оппонентом.** Выше указан VPIP. Доступны также PFR, 3-бет,
   фолд на к-бет, к-бет флоп, баррель тёрн, баррель ривер. Сокращение «ЗАК» из наброска владельца
   не опознано — нужна расшифровка.
2. **Судьба кнопки «Подробнее».** Реплей уходит в основное сообщение; кнопка либо исчезает, либо
   получает другое содержание. Здесь принято, что исчезает. Решение задевает `.claude/SESSIONS_UX.md`
   («Под вердиктом — инлайн-кнопки»): тот документ правится той же задачей, иначе разойдётся
   второй раз — ровно так, как разошлась первая редакция этого раздела.

## 6. Схема БД

jsonb — для версионированных документов-контрактов; реляционные колонки — для всего, по
чему ищем и джойним. Файлы (скрины, HH) — на диске в volume, в БД путь и хэш.

| Таблица | Ключевые поля | Назначение |
|---|---|---|
| `players` | id, tg_user_id UNIQUE, quota_daily, subscription, is_dev | сквозной уровень; израсходованное выводится из `jobs` (§9) |
| `invites` | code UNIQUE, issued_by, used_by?, used_at? | доступ по инвайтам |
| `sessions` | id, player_id, started_at, closed_at?, title | «сессия = вечер»; создаётся `/new` или молча |
| `tournaments` | id, session_id, source_file, scan_summary jsonb? | HH-вход |
| `hands` | id, session_id, tournament_id?, provenance, image_hash?, raw jsonb, canonical jsonb?, enriched jsonb?, schema_version | контракты; nullable-колонки и есть чекпоинты (§8.2) |
| `analyses` | id, hand_id, result jsonb, verdict_text?, range_images? | выход ядра и изложения; **`result` хранит документ БЕЗ точек** — их место в `decision_points` (миграция 0008), репозиторий собирает документ обратно из строк |
| `decision_points` | id, hand_id, session_id, player_id, point_no, dp_index, street, spot, zone, action_taken, best_action, ev_diff_bb, **judged**, position, to_call, pot_before, eff_stack, eff_stack_bb, spr, ev_interval jsonb?, assumption jsonb?, tools, detail | строка на точку решения. Не про скорость: с колонками фильтр становится обычным условием, и словарь запросов собирается комбинаторно, а не переписывается под каждый вопрос. Колонки обстановки nullable — у руки, не дошедшей до чекпоинта `enriched`, их неоткуда взять, и догадкой они не заполняются. `judged` пишется единственной формулировкой `contracts.is_judged` |
| `opponents` | id, owner_player_id, opponent_nick, UNIQUE `(owner_player_id, lower(opponent_nick))` | оппонент владельца по нику в руме; регистр не различается, написание хранится первое (миграции 0006, 0007) |
| `opponent_links` | PK `(owner_player_id, room_tournament_id, participant_label)`, opponent_id | сшивка «участник этого турнира — этот оппонент». Турнир записан так, как его нумерует рум, а не строкой `tournaments`: один файл бывает загружен дважды, и привязка не имеет права от этого раздваиваться — внешнего ключа на `tournaments` поэтому нет |
| `notes` | id, owner_player_id, **opponent_id UNIQUE**, color, text, updated_at | только через vision (в HH ники анонимны). До миграции 0007 заметка держала ник строкой и различала регистр, а сшивка — нет: один ник в разном написании был одним оппонентом для статистики и двумя для заметок |
| `eval_cases` | id, kind: vision_field / verdict_confirm / verdict_dispute, hand_id, field?, ground_truth jsonb, source: escalation / disagree_button / manual, created_at | этажи 2 и 4; копится сам |
| `jobs` | id, **type**, status, payload jsonb, **session_id NOT NULL**, player_id, hand_id?, attempts, max_attempts, priority, locked_by?, locked_at?, created_at, finished_at?, error? | очередь + журнал (§8) |
| `traces` | id, job_id, hand_id?, spans jsonb | что вернул каждый сервис, какие диапазоны предположены |
| `llm_calls` | id, trace_id, provider, model, purpose, tokens_in, tokens_out, cost, latency_ms, status | учёт себестоимости; точка данных лимитера |
| `calc_cache` | key (сигнатура спота), value jsonb, created_at | **включён по телеметрии и оказался решающим.** Замерено на скане турнира: 235.8 с на холодном кэше против **0.36 с на прогретом** (655×), список находок побайтово идентичен — кэш точен, потому что сэмплер детерминирован по сиду. Ключ уровня классов рук и квантованных глубин, а не конкретных раздач, поэтому **кэш общий между турнирами и между пользователями** и насыщается за первые сканы. Отсюда требование: он живёт в общем хранилище, а не в памяти воркера — иначе каждый воркер греет его заново и холодные минуты возвращаются при каждом масштабировании. |

`jobs.type`: `screenshot_analyze | hh_scan | deep_dive | eval_run | question` — поле с первой
миграции («заложить сразу» из SCALING.md), даже пока воркер один и не фильтрует. Значение
`question` добавлено миграцией 0009 вместе с `llm_calls.purpose = question_answer`: оба —
CHECK-констрейнты с закрытым набором, и без правки первая же поставленная задача падает
нарушением ограничения. Назначение вызова у вопроса отдельное, хотя модель та же, что у
`verdict_text`: `purpose` — то, по чему считается цена каждого входа продукта, и один ключ на
два входа сделал бы этот счёт невычислимым.

`jobs.session_id NOT NULL` с первой миграции: результату всегда есть куда лечь. Молчаливое
создание сессии при первом входе — обязанность `bot` с шага 6 (§13), задолго до UI сессий.

## 7. Провайдер-слой

Фасад `await llm(purpose, schema, *, prompt, images=(), tools=(), trace_id)
-> (schema_instance, meta)` — единственная дверь к моделям во всей системе.

- **Назначения** (закрытый `Literal`, он же набор в CHECK-констрейнте `llm_calls.purpose`):
  `vision_extract` и `vision_extract_fallback` (картинка → RawHand-поля, две ступени
  каскада), `verdict_text` (AnalysisResult → текст), `question_answer` (вопрос игрока →
  выбор расчёта и слова к его выходу). Каждому в конфиге сопоставлена модель строкой
  `"<provider>:<model>"` — смена вендора/модели не трогает код (PydanticAI, 20+ провайдеров).
  Требование независимости от вендора — выполняется конфигом, безболезненный A/B через evals.
- **Фасад принимает инструменты** (`tools: Sequence[Tool[None]]`) — иначе разговорный доступ
  пришлось бы строить мимо единственной двери, то есть мимо лимитера и мимо учёта в
  `llm_calls`. Инструменты собирает `calcs.routing.tools_for`, по одному на имя из
  `CalcName`; фасад про их содержание не знает ничего и остаётся транспортом.
- **Внутри фасада** (не поверх — «заложить сразу» из SCALING.md):
  - лимиты одновременности и темпа — **кросс-процессные, через Postgres** (иначе при
    `--scale worker=N` лимит молча умножается на N — тот же класс бага, что гонка миграций):
    одновременность — пул из K слотов на advisory-локах (`pg_try_advisory_lock`; лок
    сессионный, смерть воркера возвращает слот автоматически); темп — оконный счётчик по
    `llm_calls`, строка которого пишется **при старте** вызова (in-flight вызовы входят в
    окно), статус обновляется по завершении. Внутрипроцессный asyncio-семафор допустим лишь
    как локальный предфильтр, источником истины не является;
  - экспоненциальный бэкофф с джиттером на 429/5xx;
  - ретрай при ответе, не прошедшем pydantic-валидацию (1 повтор, потом ошибка задачи);
  - каждая попытка → строка в `llm_calls` (модель, токены, цена, латентность, статус).
- **Стартовые модели** (конфиг, не константа): извлечение — Sonnet-класс (точность
  критична, это главный риск конвейера), изложение — Haiku-класс (модель только излагает
  готовые числа). Vision-eval (этаж 2) — измеритель для удешевления извлечения.
- **Закладки** (интерфейс допускает, реализация по телеметрии): batch-режим для
  eval-прогонов; кэш извлечений по `image_hash` (колонка уже в `hands`); переливка на
  второго провайдера при упоре в квоту. Каскад «дёшево → дорого при непройденной проверке»
  из закладок вышел — он реализован (`vision_extract_fallback`).
- **Известный дефект: у запроса к модели нет собственного таймаута.** `agent.run()` ничем не
  обёрнут — `wait_for` вокруг вызова провайдера в периметр задачи 18 не входил и отложен
  (`platform/llm.py`, докстринг `_call_with_http_retries`). Дедлайн лимитера вызова не
  ограничивает: он абсолютный и отсчитывается на ожидание слота, а часы между попытками не
  останавливаются ни на время `agent.run()`, ни на время бэкофф-паузы — то есть зависший
  запрос молча съедает бюджет следующего `slot()`. Цена дефекта в том, что бюджет ЗАДАЧИ
  (`pipeline._JOB_DEADLINE_S`) снимает попытку целиком, вместе с уже посчитанными числами:
  один медленный вызов модели отменяет работу, которую код успел сделать до него.

## 8. Очередь и жизненный цикл задач

### 8.1 Захват и сериализация

- Захват: `SELECT … WHERE status='queued' ORDER BY priority, created_at
  FOR UPDATE SKIP LOCKED LIMIT 1` — атомарно, N воркеров не конфликтуют.
- **Одна активная задача на игрока**: воркер не берёт задачу игрока, у которого уже есть
  задача в `running`. Скрины одного игрока разбираются по порядку, чужие его не ждут;
  `queued`-задачи просто стоят в очереди и никого не блокируют.
- **`awaiting_user` активной НЕ считается**: она не занимает воркера и не блокирует
  следующие задачи игрока. Первый скрин может висеть в эскалации часами — второй скрин
  разбирается независимо.
- Приоритеты: интерактивные типы выше `eval_run`; `hh_scan` не срочен (игрок готов ждать
  минуту) — приоритет ниже скринов.
- Зависшие `running`: lock-timeout (если сессия воркера оборвалась — Postgres снимает лок;
  плюс страховочный reaper по `locked_at`) возвращает задачу в `queued`, `attempts + 1`.
  После `max_attempts` — `failed` + честное сообщение игроку.

### 8.2 Чекпоинты: станция завершена = артефакт записан

Ретрай никогда не начинает с нуля. По завершении каждой станции воркер фиксирует артефакт:

| Станция | Артефакт |
|---|---|
| Парсер | `hands.raw` |
| Нормалайзер | `hands.canonical` |
| Движок | `hands.enriched` |
| Ядро | строка в `analyses.result` |
| Изложение | `analyses.verdict_text`, PNG на диске |
| Отправка | message_id отправленных сообщений в `jobs.payload` |

При захвате задачи воркер смотрит, какие артефакты уже есть, и продолжает со следующей
станции. Следствия: повторный vision-вызов не оплачивается и — важнее — недетерминированный
LLM не выдаст игроку «другой разбор той же руки» после ретрая; отправка идемпотентна —
если message_id вердикта уже записан, повторной отправки нет.

### 8.3 Эскалация — частный случай той же точки возврата

Валидатор сказал `escalate(fields)` → воркер шлёт игроку вопрос кнопками
(`Стек героя: 12.7bb? [12.7] [12.1] [ввести вручную]`), ставит `awaiting_user`
(точка возврата уже зафиксирована артефактами) и освобождается. Ответ ловит **бот**:

1. пишет ground truth в `eval_cases` (kind=`vision_field`, привязка к руке и полю) —
   эскалация как разметочная машина из EVALS.md;
2. патчит поле в `hands.raw`, сбрасывает артефакты станций ниже по конвейеру
   (`canonical`, `enriched` пересчитаются);
3. возвращает задачу в `queued` — любой воркер продолжает.

По провенансу: скрин с несошедшимся банком → эскалация игроку; HH с несошедшимся банком →
баг парсера → `failed` + лог разработчику (игрока не спрашиваем о том, что рум записал сам).

### 8.4 Прогресс

Одно сообщение, редактируемое по станциям (`worker/pipeline._ensure_progress`).
Станций шесть — `ask | read | parse | validate | analyze | explain`, — строк игроку пять:
`read` и `parse` печатают одно «Читаю стол…». Скрин и файл раздач проходят
`Читаю стол… → Проверяю руку… → Считаю эквити… → Формулирую…`, «Подробнее» —
`Считаю эквити… → Формулирую…`, вопрос — одну строку «Считаю по вашим раздачам…».
Строки «Готово» нет: последним игрок видит сам результат. message_id прогресс-сообщения —
в `jobs.payload` (тоже переживает ретрай).

- Доступ: `/start <invite_code>` (deep-link). Без валидного инвайта — вежливый отказ.
  Квота: **скользящее окно 24 ч** — лимит считается SQL-счётчиком интерактивных задач
  игрока по `jobs` за последние 24 часа. Ни поля пояса (SESSIONS_UX его сознательно убрал),
  ни cron-сброса, ни полуночного «обнуления посреди ночной сессии» — за любые 24 часа игрок
  не потратит больше квоты. При исчерпании — сообщение с остатком и временем возврата;
  HH-скан квотой поощряется щедрее (дёшев для нас — рычаг SCALING.md).

## 10. Тесты и evals

Маппинг EVALS.md на репозиторий. Этажи 1–2 существуют до первого сквозного прохода конвейера.

### `tests/` — этаж 1, детерминированный код, CI на каждый коммит

- **Регрессионная сетка (пишется первой, сначала красная):** оба файла из `fixtures/hh/`
  (146 + 172 руки) → парсинг всех рук → каждая проходит валидатор → сохранение фишек бьётся
  → банк, пересчитанный движком, сходится с SUMMARY. Один тест накрывает парсер, нормалайзер
  и движок на 318 реальных руках.
- **Якорные тесты математики** — с каждым расчётным модулем: эквити (AKs vs QQ ≈ 46/54,
  AA vs KK ≈ 81/19), пуш-фолд против опубликованных Нэш-чартов типовых глубин, ICM на
  известных разобранных примерах, пот-оддсы по формуле.
- **Валидатор на битых руках** — синтетические негативные фикстуры (несохранение фишек,
  off-by-one позиций): валидатор обязан ловить.
- Юниты контрактов (версионирование: старый jsonb читается новой моделью) и нормалайзера —
  без инфраструктуры, конвейер чистый.
- **Тесты очереди, репозиториев и лимитера — на настоящем Postgres** (testcontainers,
  локально и в CI): семантику `SKIP LOCKED`, advisory-локов, чекпоинтов и правила
  `awaiting_user` мок не воспроизводит — тест на моке проверял бы мок, а не поведение.

### `evals/` — этажи 2–4, прогон вручную (стоят денег)

- `vision/` — пары «скрин → эталонный RawHand», старт ~20–30 размеченных; метрики: точность
  по типам полей, отдельно критичные (карты Hero, суммы), % прошедших валидатор без
  эскалации. Прогон при каждой смене vision-модели или промпта.
- `verdict/` — верность изложения: (1) все числа текста существуют в выходе ядра — кодовая
  проверка; (2) вердикт текста не противоречит знаку вердикта ядра — кодовая; (3) допущение
  зоны «предполагая» упомянуто — паттерн или дешёвый LLM-судья.
- `e2e/` — подтверждённые разборы: подтверждения и возражения (кнопка «Не согласен»)
  копятся в `eval_cases` сами; регрессия при смене модели/промпта/логики ядра.
- Прогонщик — CLI в `platform/eval_runner`: читает датасет, гонит конвейер, диффы против
  эталонов.

## 12. Деплой

- Docker Compose на VPS: `postgres` (volume + ночной `pg_dump` в cron), `bot`, `worker`.
- **Миграции — отдельный одноразовый шаг**: `docker compose run --rm migrate`
  (сервис с entrypoint `alembic upgrade head`). Entrypoint'ы `bot`/`worker` миграций
  **не катят** — иначе `--scale worker=N` даёт гонку N контейнеров за одну БД.
  Порядок деплоя: `migrate` → `up -d`.
- Конфиг и секреты — env (`.env` на VPS, не в репо). Ключи: ТГ-токен, ключи LLM-провайдеров,
  DSN БД, модели по назначениям, лимиты (семафор, темп), квоты по умолчанию.

## 13. Порядок реализации

«От проверки» (ARCHITECTURE.md): проверки существуют раньше проверяемого.

1. Каркас репо (uv, ruff, pyright, CI), контракты, перенос фикстур, **красные** тесты
   этажа 1.
2. `HHParser` + нормалайзер + движок с валидатором → **зелёная** сетка на 318 руках.

   **2a. Vision-spike (параллельно шагам 2–3, выкидной).** `scripts/spike_vision.py`:
   5–10 реальных скринов через `vision_extract` на 2–3 моделях, глазами оценить качество
   извлечения. Выход — записка с выводами (стартовая модель, сложность промпта, зоны риска),
   код throwaway. Главная неизвестность продукта (читаемость GG-скринов моделью) снимается
   на второй неделе, а не на восьмом шаге.
3. Ядро ступени «префлоп + пуш-фолд» (зона «строго») + оценщик ошибки, якорные тесты.
4. Префлоп-скан (те же инструменты циклом по файлу + пре-фильтр «сфолдил префлоп без
   решения»).
5. Платформа: БД + миграции, очередь с чекпоинтами, `llm()` с лимитером, трейс.
6. `bot` с HH-путём: файл → скан → сводка → `[разобрать]`. Молчаливое создание сессии —
   здесь. Ноль токенов — дешёвый догфудинг с реальной пользой.
7. Изложение: текст вердикта + рендер матрицы → `deep_dive` ходит насквозь.
8. Vision-парсер + эскалации кнопками (по выводам спайка 2a); vision-eval из ~20–30 скринов
   собирается до выката.
9. Сессии-UI (список, переименование, агрегат вечера), «Мои лики», заметки, инвайты, квоты.

Продукт полезен с шага 6 — до первого LLM-вызова в проде.

## 14. Границы масштабирования и отложенное

- Python достаточен: разбор I/O-bound (90% — ожидание LLM), единственная CPU-нагрузка —
  скан (секунды, `ProcessPoolExecutor` + кэш + пре-фильтр). Лестница эскалации, если
  телеметрия покажет узкое место: алгоритмика (заложена) → нативное расширение горячей
  функции (Cython/Rust через PyO3 — прецеденты в стеке: eval7, pydantic-core) → в пределе
  воркер на другом языке через ту же jobs-таблицу. Ничего из этого не реализуется сейчас.
- Замена Postgres-очереди на брокер (Redis/arq) — локальная правка модуля очереди в
  `platform/`; интерфейс `enqueue/claim/complete` контрактов процессов не меняет. Порог —
  устойчиво десятки задач/сек (тысячи одновременных пользователей).
- Разделение воркеров по `type` (`worker-fast` / `worker-heavy`) — без миграции, поле есть.
- Кэши (извлечений по `image_hash`, расчётов в `calc_cache`), каскад моделей, батчинг
  evals — включаются по телеметрии (SCALING.md).
