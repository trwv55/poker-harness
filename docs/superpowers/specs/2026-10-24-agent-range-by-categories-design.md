# Агент: диапазон соперника строит модель — по категориям кода и солверному ориентиру

Статус: код реализован 2026-10-24 (§12), промпт (§9) — не тронут, ждёт отдельной правки; вопросы §11 закрыты владельцем. §13 (ориентир сдачи) снят 2026-10-28 и заменён §14 (эквити по категориям вместо одного числа); §11 п. 4 ослаблен §14 для раскладки ривера. Код §14 реализован 2026-10-28 (§14.10), правки по ревью — §14.11; промпт (§14.7) и реплей (§14.9) — у владельца. Заменяет решение
[2026-10-23-agent-line-range](2026-10-23-agent-line-range-design.md) (колл-диапазон из долей
поля): по итогам живого прогона владелец от него отказался. Опирается на
[срез «диапазон по чарту и эквити»](2026-10-14-agent-range-slice-design.md) (§6, §12).

## 1. Зачем

Чтобы оценить ставку, нужен диапазон соперника по линии. Пробовали двумя путями, и оба
провалились:

- **Модель сужала сама** (трейсы 276–278, 2026-10-22). Она теряла классы: из восьмёрок брала
  только A8–87, из валетов — KJ–J9, пропускала гатшоты, а туз-хай с бэкдорами выбрасывала
  строкой «воздух». Флоп и тёрн расходились между собой.
- **Код строил колл-диапазон из долей поля** (`line_range`, 2026-10-24). Сдача поля на с-бет
  — 39% по всем доскам и размерам ставки. На сухом 8-8-J против трети банка сбрасывают
  больше, поэтому колл раздулся до 350 комбо, набрал K2o и Q2s, а трипсы ушли в рейз. Доли,
  усреднённые по разным бордам, состав диапазона не задают, и на нашем объёме рук их не
  сегментировать.

Решение владельца 2026-10-24: **диапазон определяет модель**. Опоры у неё такие:
- стартовый диапазон по чарту;
- солверный ориентир под похожий борд;
- собственные знания о лимитах;
- статы конкретного соперника;
- поле — последней.

Задача кода: модель не теряет классы, видит масштаб и не подменяет данные выдумкой.

## 2. Решения владельца (2026-10-24)

| вопрос | решение |
|---|---|
| колл-диапазон из долей поля (`line_range`) | убрать: доли поля по всем бордам состав не задают |
| кто решает состав диапазона | модель; это допущение, блок «Оценка модели» |
| опоры модели | стартовый по чарту → солверный ориентир по типу борда → знания модели о лимитах → статы соперника → поле в последнюю очередь |
| знания о лимитах | из самой модели, без белого списка; подаются как допущение |
| солверный ориентир | библиотека выгрузок владельца, выбор по ключу (лукап, а не поиск по смыслу) |
| классы вне чарта | модель может добавлять их сама, с названной причиной (ослабление п. 9 плана 2026-10-17) |

## 3. Что входит

1. Раскладка диапазона по категориям на борде — код (§4).
2. Сужение категориями и счёт комбо — код (§5).
3. Библиотека солверных выгрузок и лукап по типу борда — код и данные владельца (§6).
4. Добавление вне чарта по причине модели — код (§7).
5. Удаление `line_range` (§8).
6. Промпт (§9).

Не входит: ривер, мультивей, банки с 3-бетом (чартов нет), сегментация частот поля, судья
верности сужения (спека №2).

## 4. Раскладка по категориям

`opponent_range` на флопе и тёрне дополнительно печатает диапазон прошлой улицы (флоп — от
стартового), разложенный по категориям на текущем борде. Каждый класс попадает в одну
категорию — в ту, где большинство его живых комбо, при равенстве — в более слабую (§12 п. 3);
у комбо готовая рука сильнее дро. Число комбо — живые комбо с долей чарта
(`live_combos`).

Категории берутся из того, что уже считает ядро: `HandCategory` (`contracts/postflop.py`) и
дро (`analysis/tools/draws.py`).

| категория | откуда |
|---|---|
| стрит и сильнее, фулл-хаус, сет | `HandCategory` |
| трипс | `TRIPS` |
| две пары | `TWO_PAIR` |
| оверпара | `OVERPAIR` |
| топ-пара: сильный кикер / слабый кикер | `TOP_PAIR_*` |
| средняя пара, слабая пара | `MIDDLE_PAIR`, `WEAK_PAIR` |
| флеш-дро, двусторонний, гатшот, комбо-дро | `draws.py`, если готовой руки нет или она слабее пары |
| бэкдоры и старшие карты | бэкдоры и оверкарты из `draws.py` |
| ничего | всё остальное |

Пара с дро попадает в категорию пары с пометкой «+ дро»: категория одна, пометок может быть
несколько. Сначала порядок категорий как в таблице, внутри категории — классы.

Пример строки:
`трипс — 21 класс, 86 комбо: A8s, A8o (91%), K8s, …, 82s`.

Зона `strict`: это классификация руки на борде, а не догадка.

## 5. Сужение категориями

`equity_vs_range` в `hands` принимает и классы, и имена категорий из выхода §4, вперемешку.
Категория разворачивается в свои классы на этом борде. Можно убрать часть категории:
`гатшот -T7o` — категория без класса.

Выход добавляет сводку по категориям: что оставлено, сколько комбо, итог
`оставлено N комбо из M`. N и M считает код (§4). Это закрывает и пропуск классов, и
масштаб: модель видит, сколько оставила, и не может «забыть» класс внутри названной
категории.

Правила подмножества (тёрн ⊆ флоп, тёрн без флопа — отказ) остаются как есть.

## 6. Солверный ориентир

**Данные.** Библиотека выгрузок владельца в формате, который уже есть
(`solver_flop.json` эталона 001): ключ спота, борд, линия, поля `call`/`raise`/`fold`/`allin`
с долями, `*_pct`, `source`. Где лежит библиотека и публична ли она — вопрос §11.

**Ключ лукапа:**
- `(seats, position, vs_position, depth_bb, ante_type)` — как у чартов;
- улица — только флоп (выгрузок тёрна на каждую карту не набрать);
- **тип борда** (текстура) — код классифицирует флоп сам;
- **корзина размера ставки**.

**Текстура v1** (приблизительный список, утверждает владелец):
- спаренность: спаренный / нет;
- масти: радуга / две масти / одна масть;
- связность: связный / средний / сухой;
- старшинство: высокий (A или K) / средний / низкий.

**Корзины размера:** до 40% банка / 40–80% / больше 80%.

**Выбор.** Сначала точное совпадение ключа. Если его нет — та же текстура в соседней корзине
размера. Если нет и этого, ориентира нет, и модель сужает без него.

**Выход.** Отдельная строка `opponent_range` на флопе:
`Ориентир солвера (ближайшая линия: <борд выгрузки>, ставка <x>%; в руке <борд>, <y>%):
колл — <категории и классы>; рейз — …; фолд — …`.
Категории ориентира пересчитываются на борд выгрузки, так что модель сравнивает категорию с
категорией, а не класс с классом на чужом борде. Зона `strict`: выгрузка — данные владельца,
как чарт; слово «ближайшая» говорит, что борд не тот же.

**Покрытие.** Для начала владелец собирает самые частые споты: BB против BTN и CO, банк с
одним рейзом, около 15 типов флопа, 2 корзины размера — порядка 60 выгрузок. Без
выгрузки ориентира нет, и это не ошибка.

## 7. Классы вне чарта по решению модели

У `equity_vs_range` параметр `added` (п. 9 плана 2026-10-17) получает спутника `added_reason`
— причину модели одной фразой. Пример: «на низких лимитах BB часто коллирует пары, которые по
GTO 3-бетит».

- Классы игрока (`added` без причины) проверяются, как сейчас: по записи в его сообщении.
- Классы модели (`added` с причиной) проходят без записи игрока.
- Выход: `добавлено агентом (допущение): 22-77 — <причина>`. Отдельно: `добавлено по вашей
  просьбе: …`.
- Зона `assuming`, как у всего сужения.

Что модель не придумывает чарт, держится не на коде, а на подаче: каждое добавление
названо, с причиной, в блоке «Оценка модели».

## 8. Удаление `line_range`

Убираются инструмент, расчёт `_line_range`, ядро `analysis/line_range.py`, кэш `lro:`, тесты
и описание в ARCHITECTURE и SESSIONS_UX. Остаются частоты `raise_cbet` и `raise_turn_barrel`:
это обычные статы со знаменателем, они пригодятся модели (соперник часто рейзит → в колле
меньше сильных рук). Спека 2026-10-23 помечается заменённой с отсылкой сюда.

## 9. Промпт

- Порядок: `opponent_range` (стартовый + раскладка + ориентир) → решение по каждой категории
  (остаётся / уходит / частично и почему) → `equity_vs_range` категориями и классами → ответ.
- Опоры по приоритету — как в §2. Ориентир солвера — «как GTO играет на похожем борде». Свою
  поправку на лимиты модель называет: «на этих лимитах … (допущение)» в блоке.
- Статы соперника: `opponent_frequency` по нику — что он делает чаще поля (сдача на с-бет,
  рейз на с-бет). Поле — только если по сопернику пусто.
- Примеров колл-диапазонов в промпте нет: 001/002 — eval-кейсы (§11 п. 3).

## 10. Проверка

- **Тесты кода:** классификация классов по категориям на синтетических бордах (каждый класс
  ровно в одной категории; сумма комбо по категориям = комбо диапазона); развёртывание
  категорий в `hands`, вычитание класса; ключ текстуры и корзины; выбор ближайшей выгрузки;
  `added_reason`; удаление `line_range` не оставляет хвостов.
- **Эталоны:** выгрузки, попавшие в библиотеку ориентиров, не могут быть эталоном того же
  спота — модель увидит ответ. Для эталонов 001/002 нужны выгрузки, которых нет в
  библиотеке, либо эти руки исключаются из библиотеки.

## 11. Решения по открытым вопросам (владелец, 2026-10-24)

1. **Библиотека выгрузок — закрыта**: отдельный каталог данных в `.gitignore` и в
   pre-push хуке, как `evals/` и промпты. В образ стенда попадает, в гит — нет.
2. **Список текстур даст владелец позже.** До него — классификатор v1 из §6, собранный в
   одной функции и помеченный как временный; замена списка — одна правка.
3. **001/002 — eval-кейсы.** В промпт как примеры не идут и в библиотеку ориентиров не
   кладутся. Библиотека на старте пуста: ориентира нет, пока владелец не даст выгрузки.
4. **Ривер — нет.**

## 12. Реализация (2026-10-24)

Решения, где спека молчала:

1. **§8.** Код возвращён к состоянию до `7f65ef1`: сняты инструмент, `_line_range`,
   `analysis/line_range.py`, кэш `lro:`, `RangeNarrowing.by` и предпочтение `line_range` в
   `prior_for`, `range_spot(of_hero=…)` и `CalcCacheRepo.get_many` (других вызывающих не
   было). Остались частоты `raise_cbet`, `raise_turn_barrel` и отказ «тёрн без флопа»
   (`0bc6c42`). Сужения `line_range` в старых историях вечера читаются как обычные (поле
   `by` игнорируется). Хвосты закреплены `test_the_line_range_left_no_trace`.
2. **Категории §4.** Первая строка таблицы разведена на три категории по силе: «фулл-хаус
   и сильнее» (стрит-флеш, каре, фулл-хаус), «стрит или флеш» (вместе со слабыми),
   «сет». Дро — по силе: «комбо-дро» (флеш плюс стрит-дро), «флеш-дро», «двусторонний»,
   «двойной гатшот» (своя категория: `DrawKind.DOUBLE_GUTSHOT`), «гатшот». Рука «на
   борде» (`ON_BOARD`) — как без пары. Дро пометкой — у любой готовой руки, не только у
   пары. Имена — `contracts.RANGE_CATEGORY_NAMES`, без запятых и цифр (запятая делит
   `hands`, цифра стала бы числом).
3. **Класс с комбо в разных категориях** — не делится: категория большинства живых комбо,
   при равенстве — более слабая (решение оркестратора по ревью: блокер героя на ничьей
   класс не поднимает; на Q♠7♠2♠ AKo с флеш-дро у 6 из 12 комбо — в «бэкдорах и старших
   картах»); остальные категории и дро — пометками «+ <категория>», у части комбо — с
   числом: «+ флеш-дро у 6 из 12 комбо» (числа — через книгу выхода, сверка их принимает).
   У AKs на том же борде готовый флеш только у A♠K♠ — класс по большинству в «бэкдорах»,
   флеш — пометкой «у 1 из 4». Класс без живых комбо в раскладку не входит. Печать — все
   классы категории, без «…».
4. **Тёрн §4.** Раскладка — сужения флопа той же руки (`prior` от кода, как у
   `equity_vs_range`), с долями чарта, у добавленных вне чарта — 1.0; без сужения —
   стартового. На тёрне строка называет источник «ваше сужение флопа (допущение)», зона
   инструмента — `strict`, как в §4.
5. **§5.** Имя категории читается без различий в регистре, виде дефиса и тире и
   пробелах («ё» — как «е»). «-класс» — после пробела или в начале элемента (дефис внутри
   «A2s-A5s» — диапазон) и вычитается из всего названного. Отказы словами: категория без
   классов на этом борде, вычтенный класс вне названного, пустой итог, категория на ривере
   и до флопа. С весами («:») строка уходит в `narrow` как есть (прежний отказ). Сводка:
   по каждой категории раскладки исходного — «целиком», «N комбо из M, убраны: …» или
   «убрана целиком»; итог «Оставлено N комбо из M» — комбо исходного без добавленных вне
   него. Комбо сужения и доля от стартового метки не требуют: в `assumed` — только
   эквити (иначе целое совпадало бы с порогом в прозе, живой прогон 2026-10-24); они
   пересказываются в блоке «Оценка модели».
6. **§7.** С `added_reason` все классы `added` этого вызова — агента. Сужение хранит их
   с причиной (`RangeNarrowing.agent_added`); класс агента из сужения флопа (через
   `hands` на тёрне) или из последнего сужения (через `added` без причины) остаётся
   агента с прежней причиной. Строки — по одной на причину. Доля от стартового при любых
   добавленных не печатается, как раньше.
7. **§6, данные.** Каталог `src/harness/analysis/charts/solver/` — закрыт `.gitignore`,
   хуком, политикой; в колесо — через `artifacts` в `pyproject.toml` (проверено сборкой с
   подсадным файлом), в образ — `COPY src`. Файл — одна выгрузка; размер ставки — поле
   `bet_bb` или последнее «bet <x>bb» в `flop_line`, доля — к `pot_bb`. Нечитаемый файл —
   строка «библиотека ориентиров не прочиталась (…) — ориентира нет», а не отказ
   `opponent_range`.
8. **§6, ключ.** Ставка руки — первая ставка флопа, на которую соперник отвечает (не его
   собственная); банк — итог префлопа (`pot_by_street`). Позиции — правилом неполного
   стола, как у чарта защиты (`defend_table`); на ответе соперника в банке больше двух
   игроков — ориентира нет (мультивей); глубина — глубина чарта стартового
   диапазона, точным совпадением. Корзины: меньше 40%, от 40% до 80% включительно, больше
   80%. Из нескольких подходящих — ближайшая по размеру ставки, при равенстве — первая по
   имени файла. Текстура v1 — `solver_guide.texture`: связность по различным рангам в
   окне стрита из пяти (туз и младший): все три — «связный», два — «средний», иначе
   «сухой»; старшинство — A/K высокий, Q…9 средний, ниже низкий.
9. **§6, выход.** Категории ориентира считаются на борде выгрузки без карт героя (мёртвые
   — только борд выгрузки); строка на действие (`колл`, `рейз`, `фолд`, `олл-ин`).


## 13. Ориентир сдачи в выходе эквити (2026-10-24) — снят 2026-10-28, см. §14

> Оставлен как история решения; код, тесты и подсказка в выходе убираются по §14.4.

**Зачем.** Суждение модели о сужении нестабильно: на одной руке (флоп, BB коллирует с-бет)
один прогон оставил 283 комбо из 738, другой — 681 из 738, то есть BB сдаёт 8%, хотя тот же
агент называл сдачу поля на с-бет 39%. Решение владельца — не запрет, а подсказка в выходе
расчёта: противоречие модель видит сама.

**Что.** Итог сводки §5 печатается долей: «Оставлено N% диапазона на начало улицы (K комбо
из M): соперник продолжает N%, сдаёт R%», где N — `kept_combos / source_combos` с одним
знаком, R = 100 − N. Если соперник в этой руке уравнял ставку героя хедз-апом, ниже —
строка «Для сверки с долей (подсказка, сужение не меняет)» с частотой сдачи на эту ставку:
на флопе — с-бет героя, `fold_to_cbet`; на тёрне — второй баррель, `fold_to_turn_barrel`
(линия — `player_stats.hero_bet_called`, по правилам возможности этих частот). Выборка
«x из n», уровень данных и строка о выборке — как у выхода `opponent_frequency`.

**Чья статистика.** Правилом `opponent_frequency`: место соперника в этом турнире сшито с
оппонентом (`/alias`) — его частота с ником, иначе поле; окно — вся история, все позиции.
Нового порога нет: малая выборка печатается со своим знаменателем и строкой «Выборка мала»
(`MIN_STAT_OPPORTUNITIES`), подлежащее от неё не меняется.

**Когда статистики нет.** Ставил не герой (донк, ставка коллера), соперник ответил не
коллом (рейз), на его ответе в банке больше двух игроков, ривер — только доля, без частоты.
На ривере сводки нет, нет и доли.

**Не допущение и не отказ.** Числа подсказки — числа выхода (`allowed`, целый процент
ответа — половиной вверх, как везде), но в `assumed` не идут: там только эквити (§12, п. 5).
В `frequency` (опора действию соперника) частота подсказки тоже не идёт — выход эквити
измеренной частотой не считается (`test_equity_numbers_are_calculation_numbers_and_never_a_measured_frequency`);
сослаться на неё как на факт модель может через `opponent_frequency`.


## 14. Эквити по категориям вместо одного числа (решение владельца 2026-10-28)

### 14.1. Зачем

Одно общее эквити против суженного диапазона нестабильно, потому что зависит от суждения
модели о сужении. На одной руке модель оставляла 283, 681 и 326 комбо из 738, и эквити
выходило от 30% до 55%. Подсказка §13 («оставлено N%, сдаёт M%») вместе с правилом промпта
«пересузь, если расходишься со статистикой больше чем на 15 пунктов» выровняла флоп (сдача
36–45% при поле 39%), но не тёрн (23–55%). Владелец отверг саму сверку со статистикой поля.
Сдача зависит от борда и соперника и законно отличается от поля больше чем на 15 пунктов, а
порог 15 был взят на глаз.

Переносится то, что нестабильно. Состав продолжения остаётся суждением модели, но это
суждение больше не превращается в одно число, которое игрок принимает за расчёт.
Детерминированные числа считает код: эквити против каждой категории не зависит от того, что
выбрала модель. Модель говорит, какие категории соперник правдоподобно продолжает, и даёт
промежуток из чисел кода: «против его вероятных продолжений у вас от 22% (топ-пары) до 61%
(гатшоты)».

Сверка с POSITIONING: продукт обещает проверенный расчёт на руках игрока, а не эксплойт,
которого пока нет. Промежуток честнее одного числа: по категориям посчитано точно, а выбор
категорий назван допущением. Статы соперника и поправка на лимиты остаются качественной
опорой выбора и не служат порогом.

### 14.3. Почему перебор, а не Монте-Карло

Бриф просил «кэш как у нынешнего эквити (`calc_cache`, фиксированный сид)». Сид нужен
Монте-Карло, а при эквити по категориям у Монте-Карло два изъяна:

- **Цена.** Один прогон на 50 000 итераций на каждую из 10–17 категорий обходится в 10–17
  раз дороже нынешнего хода.
- **Шум.** На категории из нескольких комбо выборка мала: число дрожит от сида, хотя сид
  фиксирован.

Точный перебор проще и строже. Он даёт эквити каждого комбо сразу против всех 1081 возможных
комбо соперника. Замер в контейнере разработки (`eval7`): флоп — 0.54 с на все комбо, тёрн —
0.02 с. Это быстрее одного нынешнего прогона Монте-Карло. Эквити класса — среднее по его
живым комбо. Эквити категории — среднее эквити её классов, взвешенное живыми комбо с долей
чарта (`live_combos`). Число детерминировано без сида, а кэш по классам отдаёт любое сужение
той же руки на той же улице без пересчёта. Ничья считается половиной, как в
`turn_flop_call`.

Нынешний Монте-Карло (`tools/equity.equity_vs_range`) остаётся для прочих вызывающих.
Константы `AGENT_EQUITY_ITERATIONS` и `AGENT_EQUITY_SEED` и пространство `eqr:v1:` агенту
больше не нужны. Если других вызывающих у них нет, они снимаются.

### 14.4. Что убирается

1. **§13 целиком.** Снимаются `FoldHint`, `EquityVsRangeResult.fold_hint`, `calcs._fold_hint`,
   `player_stats.hero_bet_called` (других вызывающих нет), строки выхода «Для сверки с
   долей…» и тесты подсказки. Итог сводки §5 возвращается к виду «Оставлено N комбо из M».
   Доля «оставлено N% диапазона…: соперник продолжает N%, сдаёт R%» снимается: она
   приглашала к той же сверке со статистикой.
2. **Одно эквити.** Снимаются `EquityVsRangeResult.equity` и строка «Эквити вашей руки при
   вскрытии: N%». Строка в виде «только числа» (`presentation._equity_answer`) печатает
   эквити по категориям.
3. **`assumed`.** Снимаются метаданные `assumed` в `routing._perform`,
   `history.assumed_numbers_in` и параметры `assumed_numbers` и `summary_numbers` у
   `check_agent_answer`. Снимаются `_assumed_share_in` и исключения, которые существовали
   только ради коллизий числа эквити с другими числами прозы:
   - `_hero_chances_share` — доля сводки о шансах героя;
   - `_threshold_share` (6e2010b) — порог, привязанный к имени;
   - `_frequency_share` (3a6be0d) — частота со своей выборкой, вместе с её регэкспами.

   Вместе с ними снимаются их тесты. Блокер ревью 3a6be0d (фразы о руке героя с «колл / рейз
   / сброс» проходили без метки) закрывается снятием исключения.
4. **Остаются** 43bad47 и b60cfc0: имя порога без двоеточия («Порог фолдов у него 33%») и «как
   у (чистого) блефа» / «считать его блефом». Они закрывают ложные утверждения о сопернике
   (`_opponent_claim`), а не коллизию с эквити, и прошли ревью. Общие для них
   `_TIED_BEFORE_RE`, `_tied` и `_tied_threshold_share_in` остаются. `_AGAINST_RANGE_RE`
   остаётся, только если у него есть вызывающий кроме снятых.
5. **Промпт** (закрыт, правит владелец локально): правило «15 пунктов» в шаге 6 снимается.

### 14.5. Проверка ответа

Числа эквити по категориям из обоих выходов — числа расчёта (`allowed`, через книгу). Они не
идут ни в измеренные частоты (`frequency`), ни в `chart`, ни в `assumed` (его нет).

- **Число эквити против категории метки не требует.** Это факт: «против топ-пар у вас 22%»
  верно, что бы ни держал соперник. Прежний запрет «эквити без (допущение)» снимается вместе
  с одним числом.
- **Допущение ловится словами, как и раньше.** Слово диапазона или утверждение о сопернике
  в предложении требует метки (`_opponent_claim`), с числом или без.
- **Дыра, найденная при проектировании.** «Против его вероятных продолжений у вас от 22% до
  61%» сейчас проходит без метки: «продолжени-» не значится действием соперника. Закрывается
  узко: «продолж-» — действие соперника в части, где есть слово о нём («его», «он», «BB»,
  «соперник»…). Тест-сосед: «если вы продолжите на тёрне» и «продолжение розыгрыша» без
  соперника метки не требуют.
- **Имена категорий в ответе.** Проверка терминов сверяет их с метками руки героя («топ-пара»
  в ответе без такой метки у героя — нарушение). Значит, промежуток с именами категорий
  уходит в блок «Оценка модели», где термины не проверяются. Это уже так (EVALS: «разговор о
  диапазоне по категориям — в блоке»). Код здесь не меняется, правило держит промпт.

### 14.6. Выход (форма — для модели; слова уточняет имплементатор)

`opponent_range` — число эквити в строке каждой категории раскладки:
`топ-пара: сильный кикер — 6 классов, 24 комбо, эквити вашей руки против неё — 22%: AJs, …`.
Строки ориентира солвера эквити не несут: они на борде выгрузки.

`equity_vs_range` — сводка §5 без доли сданного. Строка «Эквити вашей руки по категориям
суженного (каждое — против этой категории, а не всего диапазона)» перечисляет категории
раскладки суженного диапазона: оставленные классы и добавленные вне исходного (у добавленных
доля 1.0, как в `prior_range`). Для каждой — комбо и эквити. Общего числа и промежутка код не
печатает: какие категории «вероятные», решает модель, а концы промежутка — числа этой строки.

### 14.7. Промпт агента (шаги 4–8; правит владелец)

- Шаг 4: `opponent_range` даёт раскладку с эквити по категориям. Читать: где больше комбо
  («в основном») и против чего рука сильна или слаба.
- Шаг 5: решение по категориям. Опоры качественные, без порогов:
  - состав и комбо категорий;
  - покерная логика линии (на колл с-бета продолжают готовые руки и дро, воздух сбрасывает);
  - ориентир солвера, если он есть;
  - статистика соперника качественно (часто сдаёт → колл сильнее);
  - поправка «на этих лимитах … (допущение)».
- Шаг 6: `equity_vs_range` категориями — запись сужения. Тёрн и ривер строятся только из
  прошлой улицы. Правило «15 пунктов» и сверка с долей сданного снимаются.
- Шаг 7: в блоке «Оценка модели» — какие категории соперник правдоподобно продолжает и
  промежуток «против его вероятных продолжений у вас от X% (категория) до Y% (категория)».
  X и Y берутся из выхода. Одного общего эквити модель не называет.
- Шаг 8: в ответе — вывод без имён категорий-терминов. Если упомянут диапазон соперника, в
  предложении нужна «(допущение)».

### 14.8. Тесты кода

- Эквити класса перебором совпадает с эталоном: AA против KK на флопе без пар и без
  стритовых и флешевых дро соперника, тёрн, ривер — исход 1/0/½.
- Детерминизм без сида; повтор отдаётся из кэша без пересчёта (по аналогии с
  `test_a_cached_equity_is_returned_without_counting_again`).
- Эквити категории — взвешенное среднее эквити её классов: доля чарта меньше 1 меняет вес.
- В выходах `opponent_range` (флоп, тёрн, ривер) и `equity_vs_range` у каждой категории есть
  своё число эквити, а общего нет.
- Ривер: раскладка без дро-категорий, «категория на ривере» больше не отказ, а ривер без
  сужения тёрна — по-прежнему отказ.
- Хвосты: нет `fold_hint`, `hero_bet_called`, `assumed`, `_frequency_share`,
  `_threshold_share`, `_hero_chances_share` (по образцу `test_the_line_range_left_no_trace`).
- Число эквити категории в ответе без метки проходит. «Против его вероятных продолжений …»
  без метки — нарушение. Соседи из §14.5 проходят.

### 14.9. Ориентир сдачи (заменяет §13 как приёмку)

Реплей двух ходов на разборе 7 («что думаешь про контбет флопа? стоило ставить?», «а второй
баррель на тёрне?»), по 5 раз каждый. Смотреть:

- выбранные категории;
- промежуток;
- состояние ответа (проза / числа / отказ);
- нарушения проверок.

Стабильность теперь меряется не одним числом, а тем, что концы промежутка — числа кода, а
набор категорий меняется между прогонами мало. Порога в коде нет: таблицу оценивает
владелец. Реплей — локально у владельца: стенд, БД и промпт в облако не попадают.


### 14.10. Реализация (2026-10-28)

Решения, где §14 молчал:

1. **Где перебор.** `turn_flop_call._equity_by_combo` вынесен в
   `analysis/tools/exact_equity.py` (`equity_by_combo`), рядом — `class_equities` (эквити
   каждого класса с живыми комбо на борде) и `group_equity` (категория). Кэш по классам —
   в `calcs` (`CLASS_EQUITY_PREFIX = "eqc:v1:exact:"`, `class_equity_key`); при промахе
   хоть одного класса считается весь борд, и в кэш уходят все классы — следующее сужение
   той же руки и улицы берёт их без перебора. `CalcCacheRepo.get_many` возвращён.
2. **Форма данных.** Эквити категории — поле `CategoryGroup.equity` (у ориентира солвера —
   `None`, и строка его не печатает). `EquityVsRangeResult.layout` — раскладка суженного
   (оставленные и добавленные классы, доли как в `prior_range`) с эквити; поля `equity`,
   `share_of_start` и `fold_hint` сняты (до флопа — `preflop_equity`, §14.11); старые
   выходы в истории читаются (лишние поля игнорируются).
3. **`share_of_start`** снят вместе с одним эквити: «N% стартового диапазона» — та же доля
   оставленного, что §14.4 снимает как приглашение к сверке со статистикой. Строка «Комбо:
   N» остаётся.
4. **Ривер.** Раскладка `opponent_range` на ривере — сужения тёрна (без него — см.
   §14.11, п. 3). Категории ривера — готовые руки и «ничего»: `draws` на ривере не
   даёт ни дро, ни бэкдоров, ни оверкарт, отдельного правила не понадобилось. `equity_vs_range`
   на ривере принимает категории сужения тёрна; без сужения тёрна отказ «сначала сузьте
   тёрн» звучит раньше разбора категорий.
5. **Префлоп** — заменено §14.11, п. 2 (было: отказ).
6. **Слова выхода.** Строка раскладки — «<категория> — N классов, M комбо, эквити вашей
   руки против неё — X%: …», в заголовке — «эквити — против каждой категории отдельно, а не
   всего диапазона». В `equity_vs_range` — «Эквити вашей руки по категориям суженного
   (каждое — против этой категории, а не всего диапазона): <категория> — M комбо, X%; …».
   В «только числах» — «Диапазон BB, суженный по линии (допущение): N комбо.» и «Эквити
   вашей руки против каждой категории: …»; подпись — «эквити по категориям суженного
   диапазона».
7. **Хвосты §13.** Сняты и `OpponentsRepo.holder` (вызывающий был один — `_fold_hint`) и
   `player_stats._HEADS_UP`. Монте-Карло `tools/equity` остался прочим вызывающим (и
   префлопу, §14.11).
8. **«Продолж-».** Действие соперника в части (делят «и», «а», «но») со словом о нём,
   проверяется раньше исключения «у вас»; глагол героя на «-ите/-ете» («вы продолжите
   против него») и прошедшее время без «бы» и повторяемости («BB продолжил коллом») —
   не утверждение (уточнено §14.11, п. 4).
9. ~~Число эквити категории метки не требует ни при каком соседстве~~ — заменено §14.11,
   п. 1.


### 14.11. Решения по ревью (владелец, 2026-10-28)

1. **Число эквити без категории — нарушение.** В ответе (`check_agent_answer`) доля эквити
   категории проходит без метки, только если в той же части предложения (её делят «,» и
   «;») названа категория — имя из `RANGE_CATEGORY_NAMES` в падежных формах (основа:
   «против топ-пар», «двух пар», «сетов»); иначе — «эквити без названной категории», если
   в предложении нет «(допущение)». Числа эквити — метаданные выхода `equity` (оба
   инструмента), из истории читаются, как `chart`. **Коллизии — одним правилом**: правилу
   подлежит только доля, которая с округлением до целого (как `_in`) совпадает с числом
   эквити и ни с одним другим числом расчётов разговора, сводки разбора, порогов, частот
   и чарта. Совпавшая доля проходит — **принятая цена** (например, эквити 32.6% против
   порога 33.3%: «у вас 33%» не ловится). Число эквити, равное другому числу того же
   выхода (комбо, доля чарта), в `equity` не пишется. Имя категории в части с числом
   эквити — о руках соперника и проверку терминов против меток героя не проходит; в
   остальных местах — как раньше. Блок «Оценка модели» — без изменений.
2. **Префлоп — одно эквити**, как до 9a99975: Монте-Карло, 50 000 итераций, сид 42,
   пространство `eqr:v1:50000:42:` (ключ — карты героя, пустой борд, суженный диапазон с
   долями). Точный перебор не взят: до флопа это 1.7 млн бордов на каждое комбо соперника.
   Поле `EquityVsRangeResult.preflop_equity`, метаданные `preflop_equity`; в ответе без
   «(допущение)» в предложении — нарушение, с тем же правилом коллизий; прежние исключения
   по словам не возвращаются. «Только числа» — одно число с «(допущение)».
3. **Сужение строго по улицам.** `opponent_range` на тёрне без сужения флопа и на ривере
   без сужения тёрна раскладки и эквити по категориям не строит: вместо них строка
   «Раскладки по категориям нет: сначала сузьте …» (`layout_refusal`), стартовый по чарту
   печатается как прежде. Флоп — от стартового. **Чек-чек тёрн** (ставок на тёрне не было
   ни у кого — читается из руки, `turn_checked_through`): ривер строится из сужения
   флопа — `equity_vs_range` на ривере не требует сужения тёрна, его исходный — сужение
   флопа, подмножество — от него; раскладка ривера — тоже из сужения флопа, источник —
   «ваше сужение флопа; на тёрне ставок не было». Ставка на тёрне была — без сужения тёрна
   отказ «сначала сузьте тёрн»; без сужения флопа — отказ всегда. Если сужение тёрна
   после чек-чек тёрна всё же есть, исходным берётся оно (`CalcRun.prior_for`: у ривера —
   тёрн, без него — флоп; годность решает ядро по руке). Подпись источника и отказ —
   «на тёрне ставок не было»: так же и после олл-ина на флопе, когда ходов на тёрне нет.
4. **«Продолж-» — о линии героя не ловится**: инфинитив и повелительное («продолжать
   против него ставку», «продолжайте ставить»), «продолжение» без «его/их» перед ним (через
   одно прилагательное) и без соперника сразу после («продолжение против него — чек»).
   «Против его вероятных продолжений», «он продолжает топ-парами», «продолжения BB» —
   ловятся.
5. Проверка, что `_violations` берёт `chart` из истории, возвращена
   (`test_the_turn_checks_read_chart_and_equity_numbers_from_history`, теперь и с
   `equity`).
6. Заголовок раскладки не обещает эквити, когда его нет (карты героя неизвестны).

9. **Уточнения по второму ревью (2026-10-28).**
   - Проверка числа эквити — лексическая: рядом названо имя категории; что число
     принадлежит именно этой категории, код не проверяет — это судья (спека агента №2).
   - Из проверки терминов вырезается только имя категории, к которой число относится по
     обороту, — «против <категория>»; «у вас сет и 45.3% против топ-пар» — «сет»
     по-прежнему термин руки героя (форма «<категория> — N%» снята третьим ревью, п. 10).
   - «Ничего» — категория только в «против ничего»; «ничего страшного» — нет. «N
     процента» — доля для правил эквити, как «N%».
   - «Продолж-»: инфинитив освобождает только без соперника-подлежащего в части
     (предлог с дополнением — «против него», «против BB» — подлежащим не считается);
     «продолжения у BB» — утверждение.
   - **Решения владельца:** (а) ривер — от последнего актуального сужения; пересужение
     ранней улицы сбрасывает поздние: по порядку сужений в разговоре (`CalcRun.actual_for`)
     новое сужение флопа после сужения тёрна делает сужение тёрна (и ривера) устаревшим —
     оно больше не исходное ни для ривера, ни для раскладки `opponent_range`. Ставка на
     тёрне была — ривер требует сузить тёрн заново, отказ «сначала сузьте тёрн: флоп сужен
     заново …»; на тёрне ставок не было — ривер от нового сужения флопа. Новое сужение
     тёрна так же сбрасывает ривер. Сброшенные улицы код передаёт расчёту параметром
     `reset`. (б) Числа, которые напечатал игрок, правило коллизий не освобождают.
10. **Третье ревью (2026-10-28).**
   - Категория для правила эквити и освобождение от проверки терминов — **только оборот
     «против <категория>»** (любой пробел после «против», и неразрывный). Форма
     «<категория> — N%» снята: «У вас сет — 45.3% против топ-пар», «У вас флеш-дро — 45.3%»
     открывали пропуск термина героя. Перечень «топ-пары — 22%» в ответе категорию не
     называет — нужно «против» или метка; перечню место в блоке «Оценка модели».
   - «Они» — слово о сопернике. Вводное слово в запятых («скорее всего», «вероятно»,
     «по-видимому», «видимо», «наверное», «возможно») придаточное не делит: «BB, скорее
     всего, продолжит» — утверждение.
   - Позиция соперника — без различий в регистре («bb» и «BB» — один соперник; с п. 11 —
     приведением на границе инструмента, а не сравнением в истории). Пересужение префлопа сбрасывает флоп: отказ тёрна — «сначала
     сузьте флоп: префлоп сужен заново …». `reset` проходит от `tools_for` до расчёта
     (сквозной тест).
   - **Принято как есть:** после обрезки истории по токенам старое сужение может уйти, и
     формулировка «сужен заново» теряется — сам отказ остаётся; существительные
     «склонен к продолжению», «ждать продолжения» без «его/их» механика пропускает — это
     судья.
11. **Четвёртое ревью (2026-10-28).**
   - Вводные слова: список расширен («вероятнее всего», «похоже», «наверняка», «по всей
     видимости», «судя по всему», «очевидно», «кажется», «думаю», «пожалуй»), формы в тире
