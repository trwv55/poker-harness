# Заметки: вход без скриншота и личные цвета игрока

Статус: спека на ревью владельца. Решения владельца приняты 2026-10-01 (бриф задачи) и
2026-10-03 (диалог) и записаны здесь; отдельный план не пишется — подзадачи и гейты в §9
(указание владельца 2026-10-03).

## 1. Зачем

Подписи цветов заметок зашиты в коде (`contracts.history.NOTE_COLORS`: red «агрессор»,
yellow «лузовый», green «слабый», blue «тайтовый»). Набор выбрал имплементатор, а не
владелец, и у всех игроков он один. Владелец хочет, чтобы каждый игрок называл свои
цвета своими словами.

Вторая проблема обнаружилась при постановке: **новую заметку сегодня завести нельзя.**
Заметка заводится только кнопкой под разбором руки, а кнопки строятся лишь для
оппонентов с ником (`keyboards.note_nicks_for_hand`, фильтр `Identity.NICK`). Ник есть
только у рук со скриншота; в файлах PokerCraft участники обезличены, а приём скриншотов
выключен с 2026-09-17. Экран «Заметки» новых не заводит (решение владельца 2026-09-04).
Цвета без входа для заметок проверить вживую нечем.

## 2. Решения владельца

| вопрос | решение | дата |
|---|---|---|
| порядок | **оба в одной задаче**: сначала вход для заметок, затем цвета; два отдельных коммита | 2026-10-03 |
| форма команды | **две формы**: `/note Ник` открывает тот же ввод, что кнопка под разбором; `/note Ник текст` — первое слово ник, остальное сразу дописывается; с переносом строки ник — вся первая строка (ник из нескольких слов), запись — со второй | 2026-10-03 |
| чьи цвета | у каждого игрока свои цвета и подписи; хардкода нет | 2026-10-01 |
| откуда цвета | игрок называет метки словами («зелёный — слабый, коллер»), бот записывает как есть; палитру эмодзи не предлагать | 2026-10-01 |
| новый игрок | цветов нет вовсе; без заметок продукт опирается на классы диапазонов | 2026-10-01 |
| где правятся | в «Настройках» | 2026-10-01 |
| хранение | **подход A**: отдельная таблица `note_colors`, заметка ссылается составным FK | 2026-10-03 |
| ввод цветов | экран «Цвета заметок» сам открывает ввод: подсказка формата на нём и есть просьба написать | 2026-10-03 |

Подходы, отклонённые при согласовании: jsonb-палитра в `players` и имя цвета строкой в
`notes` (переименование и удаление цвета обходят заметки кодом, чужое имя в колонке ничем
не запрещено); фиксированные ключи с подписями игрока (это палитра, решение 2026-10-01).

## 3. Часть 1 — команда `/note`

Роутер получает `Command("note")` рядом с `/alias`; обработчик
`handle_note_command(deps, tg_user_id, args)` в `bot/handlers.py`.

| вход | что делает | ответ |
|---|---|---|
| `/note` | ничего не пишет | `note_usage_msg`: формат обеих форм |
| `/note Ник` | ставит `pending_input = {"kind": "note", "nick": Ник, "mode": "append"}` — ровно то, что ставит кнопка под разбором | `note_prompt_msg(nick, existing, append=True)` с прежним текстом, если он есть |
| `/note Ник текст` | первое слово — ник, остальное — запись; `NotesRepo.append` строкой с датой сверху | `note_appended_msg(nick)` |

Пределы те же, что в продукте уже есть, и второго числа не появляется:

- ник не длиннее `_MAX_NICKNAME` (64): набирается руками, как у `/alias` → `gg_nickname_too_long_msg`;
- запись не длиннее `MAX_NOTE_ENTRY_CHARS` → `note_too_long_msg(limit)`, ничего не записывается.

Ник без учёта регистра — через `OpponentsRepo.get_or_create`, это уже так в
`NotesRepo.append`. Если в аргументах есть перенос строки, ник — вся первая строка (в том
числе из нескольких слов), запись — остальное; без записи это форма «открыть ввод» на этот
ник. Без переноса ник — первое слово, остальное — запись: `/note Big Fish` одной строкой —
ник Big и запись Fish (решение владельца 2026-10-03).

Команда не гасит начатый ввод другого рода (как `/ask`): `/note Ник` его заменяет своим,
`/note Ник текст` пишет мимо и оставляет начатое ждать.

Документы, которые это меняет: строка `notes` в тех-спеке §6 («только через vision» —
больше неверно), докстринг `NotesRepo` («живут только на vision-пути»), `SESSIONS_UX.md`
(пункт «Заметки» и новый раздел «Команда `/note`»), `help_msg`.

## 4. Часть 2 — схема

### 4.1 Таблица `note_colors`

| колонка | тип | примечание |
|---|---|---|
| `id` | BigInteger PK | |
| `player_id` | BigInteger FK `players.id` NOT NULL | |
| `name` | String(32) NOT NULL | как написал игрок, первое написание хранится |
| `meaning` | String(120) NOT NULL | подпись словами игрока |
| `created_at` | DateTime(tz) NOT NULL | |

Ограничения: уникальный функциональный индекс `(player_id, lower(name))` — тот же приём,
что у `opponents`; `UNIQUE (id, player_id)` (`uq_note_colors_id_player`) — цель составного
FK, сам ничего не проверяет.

### 4.2 `notes.color` → `notes.color_id`

`color_id BigInteger NULL`; составной FK `(color_id, owner_player_id)` →
`note_colors(id, player_id)` (`fk_notes_color_note_colors`), без каскада: удаление
цвета обнуляет `color_id` кодом в той же транзакции (§6), а каскадом заметка бы исчезла.
Колонка `color` удаляется.

### 4.3 Миграция 0013

Номер **0013**, не 0012: `0012_decision_points_mismatch` уже занят (коммит db9a079).

Upgrade: создать `note_colors`; добавить `notes.color_id`; для каждой пары
`(owner_player_id, color)` с `color <> 'none'` завести цвет владельцу с прежней подписью
и проставить `color_id` его заметкам; удалить `notes.color`. Соответствие:

| старый ключ | `name` | `meaning` |
|---|---|---|
| red | красный | агрессор |
| yellow | жёлтый | лузовый |
| green | зелёный | слабый |
| blue | синий | тайтовый |

Ключ вне этих четырёх в колонке оказаться не мог (`_set_note_color` сверял с
`NOTE_COLORS`), но если оказался — переносится как `name = ключ, meaning = ключ`: терять
метку молча нельзя.

Downgrade: вернуть `notes.color` с `'none'`; заметкам, чей цвет по `lower(name)` совпадает
с одним из четырёх имён таблицы выше, вернуть старый ключ; остальные цвета **теряются** —
назвать это в докстринге миграции. Удалить `color_id` и `note_colors`.

Перенос закреплён тестом на отдельном контейнере по образцу
`test_migration_0007_collapses_notes_of_one_nick_in_two_cases`: upgrade до `0012`,
посадка заметок с цветами у двух владельцев, upgrade до `0013`, проверка; затем downgrade
до `0012` и проверка возврата ключей.

## 5. Часть 2 — контракты и разбор ввода (`contracts/history.py`)

- `NoteColor(key, label)`, `NOTE_COLORS`, `NOTE_COLOR_NONE` удаляются. Вместо них
  `NoteColorRecord(color_id, name, meaning)`.
- `NoteRecord.color: str` → `color: NoteColorRecord | None`.
- `MAX_NOTE_COLOR_NAME_CHARS = 32`, `MAX_NOTE_COLOR_MEANING_CHARS = 120`,
  `MAX_NOTE_COLORS = 12` — потолок на игрока, чтобы экран и кнопки влезали в одно сообщение.
- `parse_note_colors(text) -> list[tuple[str, str]]` — **код, не модель** (CLAUDE.md: LLM в
  конвейере только для ответа на вопрос). Правила:
  - одна непустая строка — один цвет; пустые строки пропускаются;
  - разделитель — первое вхождение «—», «–», «:» или « - » (дефис **только с пробелами
    по бокам**: иначе «тёмно-зелёный — слабый» резалось бы по дефису);
  - обе половины обрезаются от пробелов; пустая половина, строка без разделителя,
    превышение пределов длины — `ValueError` с номером и текстом строки; **ничего из
    набора не записывается**: половинчатая запись выглядела бы как успех;
  - одно имя дважды в одном сообщении без учёта регистра — последняя подпись
    побеждает (игрок правит себя в том же сообщении).

## 6. Часть 2 — хранилище (`memory/`)

`NoteColor(Base)` в `models.py`; новый пункт 7 списка отступлений от §6 в модульном
докстринге.

`NoteColorsRepo`:

- `upsert_many(player_id, pairs)` — имя без учёта регистра то же → обновляется
  `meaning`, написание имени остаётся первым; новое — вставляется. Если после записи
  цветов у игрока стало бы больше `MAX_NOTE_COLORS` — `ValueError`, ничего не записано.
- `list_for_player(player_id)` — в порядке `created_at, id`.
- `delete(color_id, player_id) -> bool` — в одной транзакции сначала
  `UPDATE notes SET color_id = NULL WHERE color_id = :id AND owner_player_id = :player`,
  затем удаление; `False` — цвета нет или он чужой.

`NotesRepo`:

- `set_color(note_id, owner_player_id, color_id: int | None) -> bool` — цвет сверяется
  с владельцем **до** записи (`select` из `note_colors`), а не ловится ошибкой FK:
  `False` — заметки нет, она чужая, или цвет чужой/несуществующий.
- `upsert` теряет параметр `color`: цвет ставится только отдельной кнопкой, правка
  текста его не трогает — это уже закреплено тестом, параметр был мёртвым путём.
- выборки джойнят `note_colors` и заполняют `NoteRecord.color`.

## 7. Часть 2 — бот и экраны

### 7.1 Ввод цветов

Новый вид `players.pending_input`: `{"kind": "note_color"}`. `_apply_pending_input`
разбирает текст `parse_note_colors`, пишет `upsert_many`, гасит ввод и отвечает экраном
цветов (§7.2) с первой строкой «Записал N цветов». Ошибка разбора или потолок — отказ с
указанием строки, ввод **не закрывается**: игрок правит строку, а не начинает путь заново
(как у слишком длинной заметки).

### 7.2 «Настройки» → «🎨 Цвета заметок»

Кнопка `SETTINGS_COLORS_DATA = "notecolors"` под `settings_msg`. Экран `note_colors_msg`:

```
Цвета заметок

зелёный — слабый, коллер        [🗑 зелёный]
красный — агрессор              [🗑 красный]

Напишите свои цвета, по одному в строке: «цвет — что он значит».
Например: зелёный — слабый, коллер. Тот же цвет новой строкой меняет подпись. Не больше 12 цветов.
```

Без цветов — вместо списка строка «Цветов пока нет.» и та же подсказка. Открытие экрана
ставит `pending_input = {"kind": "note_color"}` — следующий текст и есть цвета
(решение владельца 2026-10-03). Кнопка нижнего меню, как и везде, ввод снимает.

Кнопка «🗑 имя» — `notecolordel:{color_id}`: удаляет цвет, обнуляет его у заметок,
отвечает обновлённым экраном (и снова открывает ввод).

### 7.3 Кнопка «Цвет» у заметки

`note_color_prompt_msg(note, colors)`: кнопки — цвета игрока по одной в ряд
(`notecolorset:{note_id}:{color_id}`) плюс «⚪️ без цвета»
(`notecolorset:{note_id}:none`). Если цветов нет — текст «Цвета ещё не заданы: задайте
их в ⚙️ Настройки → 🎨 Цвета заметок.» и ни одной кнопки цвета.

`_set_note_color`: `none` → `None`; нецифровой или чужой id → `note_gone_msg` (как сейчас
для неизвестного ключа). Ответ `note_color_saved_msg(nick, «имя — подпись»)` либо
`«Vasya — без цвета.»`.

### 7.4 Экран «Заметки»

`_note_lines`: с цветом — `«зелёный — слабый, коллер · Vasya»`, без цвета — только ник.
Бюджет одного сообщения: тест на самые длинные заметки
(`test_notes_msg_of_the_longest_notes_still_fits_one_telegram_message`) пересчитывается
с самым длинным цветом (32 + 3 + 120 знаков).

### 7.5 Префиксы и порядок разбора

`UI_CALLBACK_PREFIXES` пополняется `SETTINGS_COLORS_DATA` и `NOTE_COLOR_DELETE_PREFIX`
(`notecolordel:`). Порядок в `_dispatch_ui`: `notecolorset:`, `notecolordel:`, затем
`notecolor:` — общий префикс проверяется последним (правило уже записано в докстринге).

## 8. Чего не делаем

- Кнопок заметок под разбором для оппонентов, привязанных `/alias`: кнопки строит воркер
  из руки до того, как привязка сделана; отдельная задача.
- Чтения цвета движком: сегодня цвет не читает ни один расчёт; «диапазон по приоритету
  заметки → архетип → популяция» из ARCHITECTURE остаётся отложенным.
- Экрана «Заметки», заводящего новые заметки (решение владельца 2026-09-04 в силе —
  вход даёт команда).
- Палитры и эмодзи у цветов: цвет — слово игрока.
