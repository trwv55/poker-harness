# Агент: оболочка диалога, инструменты `/ask`, снятие `/ask`

Статус: спека на ревью владельца. Решения приняты в диалоге 2026-10-11 и записаны здесь.
Это первая из четырёх спек агента (§10); исходный замысел — документ владельца
«Агент разбора рук: что мы от него ждём».

## 1. Зачем

Первый разбор руки или HH собирает и отдаёт код — так остаётся. Дальше игрок хочет
уточнять: «почему здесь фолд», «как часто он фолдит на c-bet», «где я теряю за вечер».
Сегодня для этого есть только `/ask`: одна команда, один вызов модели, один расчёт,
без истории — следующий вопрос не знает предыдущего.

Агент заменяет `/ask`: любое свободное сообщение — вопрос, разговор живёт до конца
вечера, за один ответ можно вызвать несколько расчётов. Граница прежняя: **агент
маршрутизирует и излагает, считает код**. Каждое число в ответе обязано прийти из
расчёта или из разбора, иначе проза не показывается.

## 3. Поток

```
текст игрока
  → bot.handle_text: меню? → pending_input? → ждёт ручной ответ по эскалации? → иначе:
  → проверка доступа (is_dev) и квоты → JobsRepo: задача type="agent", payload {text}
  → worker._run_agent:
       контекст (сводка последнего разбора или пусто)
       + история вечера из sessions.agent_history
       → llm(purpose="agent", tools, message_history)
       → проверки ответа (§6) → при провале одна попытка переписать
       → presentation: одно из трёх состояний (§7) → отправка игроку
       → запись истории (только после удачной отправки) и журнала
```

Сообщения одного игрока обрабатываются по очереди: `uq_jobs_player_id_running` уже не
даёт двум задачам игрока выполняться одновременно, поэтому запись истории не гоняется.
Очередь `jobs` одна на всех, отдельной для агента нет. Следствие: вопрос, заданный во
время долгого скана HH того же игрока, ждёт конца скана. Для v1 принято (решение
владельца 2026-10-11); если на стенде мешает — задачи агента получат свою сериализацию
вне общей.

Свободный текст, пока ждём ручной ответ по эскалации, остаётся эскалации (сегодня не-число
там получает `vision_answer_not_a_number_msg`). Игрок, который в это время задаёт вопрос,
получит это сообщение, а не агента — известный и принятый край.

## 4. Контекст

- **Указатель.** `sessions.last_analysis_id` — последний разбор (рука или HH) вечера;
  каждый новый разбор его перезаписывает. Агент отвечает про него, пока игрок не загрузит
  новый.
- **Сводка собирается кодом** из разбора: рука, позиции, стеки в BB, борд, линия по
  улицам, метки классификатора, решения с вердиктами и зонами. Сборка идёт через
  `NumberBook` (`explanation/digest.py`), так что каждое число сводки сразу разрешено.
  Источники: `AnalysesRepo`, `decision_points`, `explanation.hand_replay`,
  `PointVerdict.detail["postflop_line"]`.
- **Без разбора** сводки нет; агент работает только инструментами статистики.

## 5. Инструменты

Шесть расчётов `/ask` переходят как есть, через `calcs.routing.tools_for` / `_perform`:
`hero_frequency`, `opponent_frequency`, `coverage`, `leaks`, `defense_frequency`,
`frequency_vs_threshold`. Сессия по-прежнему берётся из задачи, а не от модели
(`_window`); ник соперника — через `OpponentsRepo` (`_opponent_id`).

Что меняется в маршрутизации:

- **Ограничение «один вопрос — один расчёт» снимается.** Его роль — защита от перебора
  срезов — переходит к правилу «лик только из `leaks`» (§6) и к правилу выборки.
- **Потолок — 8 вызовов на ход.** Девятый получает отказ, как сегодня второй.
- **Ответ без вызова допустим**, если все его числа из сводки разбора: вопрос про руку
  часто отвечается контекстом. Ответ без вызова и без разбора — отказ, как сейчас.
- Подпись «Посчитано: …» — список всех расчётов хода, собирает `presentation` по
  `CalcResult.calc`, не модель. Расчётов в ходе нет — подпись называет те источники, что
  есть: «разбор раздачи» и/или «расчёты выше в этом разговоре».
- **Банк и ставка от модели — только из известного** (решение контроллера 2026-10-11 по
  финальному ревью, только у агента; `/ask` как был). У агента эти размеры в BB, как в разборе
  (`pot_before_bb` / `bet_bb` у `defense_frequency` и у порога `bet_size`; у `/ask` —
  `pot_before` / `bet` в фишках): сводка печатает суммы в BB. Они должны быть положительными
  и быть числами сводки разбора, реплик игрока или выходов расчётов вечера; иначе инструмент
  не считает и отвечает модели отказом — взять размеры оттуда или спросить игрока. Внутрь
  расчёта размеры идут целыми сотыми долями BB (выход зависит только от отношения ставки к
  банку), а модели и игроку показываются те BB, что передала модель.

Новые инструменты (эквити, ауты, пороги, пуш-фолд, чарт, сетка 13×13, комбо, категории)
— спека №3.

## 6. Проверки ответа

Все проверки — код, одна реализация для прода и evals (`explanation`, рядом с
`check_answer`; EVALS.md требует общей реализации).

| проверка | как | при провале |
|---|---|---|
| числа | каждое число — в разрешённых: сводка разбора ∪ выходы всех расчётов, которые остались в истории вечера ∪ числа реплик игрока (без обозначений карт) | переписать |
| обозначения карт | `99`, `A5s`, `T9o`, ранги в описании борда числами не считаются (закрывает часть §5.7 тех-спеки) | — |
| «(допущение)» | предложение, которое говорит о сопернике (он, его, соперник, поле, позиция, «такие игроки», регуляры) и о том, что он держит или сделает (диапазон, пары, бродвеи, `Jx`, сбрасывает, защитит, коллирует…), несёт буквальную метку «(допущение)», даже с «если»; не требуют её только действие, привязанное к доле или «N из M» из расчёта («сбрасывать 24% диапазона», «сбрасывало 30 из 50»), и метаречь («про его диапазон это мало говорит») (решение владельца 2026-10-13, правка контроллера по ревью); новая функция — `has_assumption_words` ловит голое «если » и для этого не годится | переписать |
| «в плюсе» | голый вывод «в плюсе» / «в минусе» / «окупается» — только если в разговоре есть `frequency_vs_threshold` с выводом выше или ниже порога («не определено» не считается); с долей и условием («от 19.4% эквити», «при 24% фолдов», «если … чаще 24%») это арифметика и допустимо (решение владельца 2026-10-13, правка контроллера) | переписать |
| термины | термин из словаря (c-бет, донк, проба, баррель, чек-рейз, категории рук и дро) совпадает с меткой классификатора у того действия, о котором речь; отрицание («без флеш-дро», «нет …», «не …») термином не считается | переписать |
| «лик» | слово «лик» допустимо, только если в этом вечере вызывался `leaks` | переписать |
| лучшая линия | на флопе и тёрне — словарная проверка оборотов «лучшая линия», «лучше было», «GTO», «правильно было», «правильная линия» по этим улицам; «стоило» снято 2026-10-13 — это слово вопроса игрока; `names_the_better_line` не подходит, ему нужен `best_action`, которого там нет | переписать |
| ошибка | `error_words_in` — как сейчас | переписать |

Механическая проверка допущений и лучшей линии частичная: она ловит явные обороты,
остальное ловит судья (спека №2). Это записывается в EVALS.md как граница, а не как
гарантия.

**Попытка переписать** — второй вызов модели с тем же контекстом и списком нарушений.
Это не схемный повтор внутри `llm()` (`_MAX_SCHEMA_ATTEMPTS`) — два разных механизма.
Вторая попытка не прошла — игрок получает числа без прозы.

## 7. Подача

Три состояния, как в SESSIONS_UX для `/ask`:

1. **Проза + «Посчитано: <список расчётов>»** — проверки пройдены; под прозой только эта
   строка, без чисел расчётов (решение владельца 2026-10-13).
2. **Числа без прозы** — проза не прошла дважды; выходы расчётов в виде, собранном кодом.
3. **Отказ** — нет ни расчёта, ни разбора; со списком того, что агент умеет считать.

Под состояниями 1 и 2 — кнопка «не то посчитано» (§8). Длинный ответ режется по 4096
символам существующим правилом. Пока задача идёт — индикатор «печатает» вместо
`_ensure_progress`. Числа, BB, знаменатель, «наблюдений нет» вместо 0% — по SESSIONS_UX
(«знаменатель всегда, интервал никогда»). Все тексты — в `presentation/messages.py`.

## 8. Данные

Миграция:

- `sessions.agent_history` JSONB null — сериализованные сообщения pydantic-ai
  (`ModelMessagesTypeAdapter`); `sessions.last_analysis_id` FK → `analyses` null.
- `jobs.type`: `question` → `agent`. `llm_calls.purpose`: `question_answer` → `agent`.
  CHECK-ограничения обеих колонок правятся той же миграцией.
- `eval_cases.hand_id` → nullable (вопрос без руки); `kind` и `source` получают значение
  для «не то посчитано».

**История** живёт в сессии и уходит с её закрытием (`/new` или тихое закрытие).
Потолок истории в токенах: при превышении отбрасываются самые старые ходы целиком, вместе
с выходами их расчётов — числа из них перестают быть разрешёнными. Значение потолка
задаётся конфигом и выбирается при реализации по размеру контекста модели.

**Журнал** — `traces`, одна строка на задачу, то есть на ход агента. В `spans` через
`Trace.record`: вопрос; каждый вызов (имя, параметры, выход, зона, время); результаты
проверок и была ли попытка переписать; исход (1/2/3). Журнал живёт дольше истории: он для
разборов и evals. Это закрывает долг EVALS «выбранный расчёт нигде не пишется».

**Кнопка «не то посчитано»** пишет ход в `eval_cases` (вопрос, вызовы, ответ, ссылка на
trace) — кандидат в eval-набор маршрутизации.

## 9. Модель, лимиты, квота

- **`llm()`** (`platform/llm.py`) получает: аргумент `message_history`, назначение
  `agent` (модель — `LLM_AGENT_MODEL`, по умолчанию Sonnet 5.5), таймаут на запрос к
  провайдеру (сегодня его нет — дефект из тех-спеки).
- **Лимитер** считает каждый запрос к провайдеру, а не каждый `agent.run()`: сегодня ход с
  несколькими вызовами инструментов пишет одну строку `llm_calls` и недосчитывается.
- **Дедлайн задачи** `agent` — 120 с, как у `question`; цель задержки — до 30 с.
- **Квота**: задача `agent` входит в `QUOTA_INTERACTIVE_JOB_TYPES`, одна единица на
  сообщение; упавшая задача бесплатна (`QuotaRepo`). Подпись «разборов X/Y» → «запросов
  X/Y» (`_quota_line`, `quota_exceeded_msg`).

## 10. Промпт, доступ, снятие `/ask`

**Системный промпт** — `src/harness/agent/prompts/system.md` (путь уже закрыт pre-push
хуком: `src/harness/[^/]+/prompts/`). Содержит: роль (тренер MTT micro/low/middle, GG),
правила утверждений (факт / допущение), процедуру работы со статистикой (порог 20
возможностей, стат под спот), процедуру чтения диапазона по линии (стартовый — только из
расчёта, сужение — допущение), запрет вердикта о лучшей линии на флопе и тёрне, суждение
против диапазона, а не вскрытой карты, «лик» только из `leaks`, отказ от живых советов во
время игры, нет PKO. Черновик пишет Claude, правит владелец.

**Пакет.** Новый `harness.agent`: запуск агента, история, сборка инструментов. Ему нужна
база (как `calcs`), поэтому он не конвейерный. Чистые части — сводка и проверки — в
`explanation`.

**Доступ:** `players.is_dev`. Остальным свободный текст отвечает как сегодня, и у них
остаётся `/ask` — иначе до открытия агента игроки теряют вопросы вовсе.

**Снятие `/ask`** — в момент открытия агента игрокам (после спеки №2); код удаления
готовится и проверяется здесь, включается тем же переключателем доступа. Уходят: команда в роутере, `handle_question_command`, `_run_question`,
`answer_question`, отказ на второй расчёт, `question_msg` / `question_refusal_msg` и их
тесты. Отказ «один расчёт» уходит вместе с тестом
`test_the_second_calculation_is_refused`; его смысл переносится в §6.

правило агента — возможности конкретного стата. Обе называются в документах явно.

## 12. Тесты

pytest без настоящей модели: `TestModel` / `FunctionModel` pydantic-ai.

- маршрутизация текста: меню, начатый ввод, эскалация, агент; не-`is_dev` — как сегодня;
- квота: сообщение агенту тратит единицу, упавшее — нет;
- история: запись, чтение, закрытие сессии стирает, обрезка по потолку убирает и числа;
- каждая проверка §6 — по тесту на провал и на проход; обозначения карт не числа;
- попытка переписать: одна, затем числа без прозы;
- потолок 8 вызовов; ответ без вызова из чисел сводки проходит, без сводки — отказ;
- журнал: вызовы, проверки, исход в `spans`; кнопка пишет `eval_cases` без `hand_id`;
- лимитер: ход с тремя вызовами модели считается тремя.

Гейт: `uv run pytest -q -ra` (смотреть `skipped`), `uv run ruff check . && uv run
pyright`. Затем — проверка вживую на стенде владельцем (`is_dev`), с пересборкой образа и
сверкой SHA.
